### 1.3 "08시트는 상위 P/N 4개를 한 칸에, 14행이 평면" — **참**. 시트가 말하는 것과 말하지 않는 것

- `08!A2` = `상위 P/N:`, `08!B2` = **`FS-7010 / FS-7020 / GB-8000 / PL-9000`** (한 칸, 병합 아님, 구분자 ` / `). `C2` 는 빈 칸.
- 데이터 `R04:R17` = 14행. `A` 열(Level)은 **14행 전부 `L2`**. 부모를 가리키는 열이 **없다**.
- `H` 열은 전부 `=E*G` (단가×수량), `H18 = SUM(H4:H17)`. 즉 08은 **원가 집계 시트**이고 트리 시트가 아니다.

| 08시트가 **말해주는 것** | 08시트가 **말하지 않는 것** |
|---|---|
| 이 14행의 부모는 그 4개 **집합** 안에 있다 | 어느 행이 어느 부모에 붙는지 (행↔부모 매핑) |
| 행별 `Qty/상위`(E)·단위(F)·소요합계(H) | `L2` 가 어느 부모 기준의 L2 인지 |
| 부모 4개의 완성품당 합이 4 라는 것(F2 수식) | FS-7010 이 자식을 갖는지 (R04 에 FS-7010 자신이 들어 있다 = 자기참조) |
| P/N 접두(FS-70/GB-80/PL-90)로 계열 추정이 가능하다는 것 | **OR-7025 처럼 접두가 계열과 안 맞는 행**(OR-)의 소속 |

→ **08 단독으로는 FS-7021·FS-7022·OR-7025 의 부모가 미확정이다.** 계획서 §9.2 P-16 이 이 셋을 "부모 추정" 이라 부른 근거는 여기까지는 옳다. 그러나 원천은 08 하나가 아니다 → 1.4.

## 2. OR-7025 의 부모 — 원천이 판정 가능한가

| 근거 | 내용 | 가리키는 부모 |
|---|---|---|
| `09!C43` | 상위 P/N = `FS-7020`, 상위 SubAssy = `Flange Shaft No.2 Assy`, 2 EA | **FS-7020** |
| `08!R08` | `OR-7025 / O-Ring (Shaft Seal) / NBR / 2 EA` — 부모 칸 없음 | 4개 중 하나 |
| 품명 `Shaft Seal` · 수량 2 | 실링 대상이 "메인 출력축"(FS-7010) 쪽일 수 있다는 **설계 직관** | FS-7010 (가설) |
| PDF | `OR-7025` 언급 없음 | — |
| JSON `parts[]` | `parentPn: "FS-7020"` (09시트를 그대로 옮긴 것) | FS-7020 |

**판정: 원천은 판정 가능하다. 영구 미확정이 아니다.**
09시트가 `FS-7020` 이라고 한 줄로 적었다. "FS-7010 쪽일 수도" 는 **원천 진술이 아니라 품명에서 나온 가설**이고, 그 가설을 지지하는 원천 문장은 한 줄도 없다. 게다가 09시트는 `FS-7010` 의 유일한 자식으로 `FS-7010` 자신만 적었다(R39) — **FS-7010 은 자식이 없는 단품**이라고 09가 말한 셈이다.

부모를 FS-7010 으로 옮기려면 원천을 **뒤집는** 것이고, 그 대가는 실측했다(§3 E-10):
- `FS-7010` 이 BOM 을 갖는 순간 `item_type='PT'` 인 채 BOM 헤더를 소유한다 — 이를 막는 트리거도 점검 뷰도 **없다**(조용히 통과).
- 기존 `FS-7020 > OR-7025` 라인은 **DELETE 가 거부된다**(`R-11: 승인된 BOM 의 라인은 삭제하지 않는다 — valid_to 를 끊어라`). ECO + `valid_to` 절단 경로만 가능.
- 절단 전에 두 라인이 동시 유효하면 `v_bom_line_qpp` 는 `FS-7020=2.0, FS-7010=2.0` 두 줄(= 완성품당 4 EA)이 되는데, **호환 뷰 `parts` 는 `MIN(line_id)` 로 한 줄만 남겨 `FS-7020` 만 보여준다** — 화면에서 안 보이는 이중계상이다(E-11).
- `FS-7010` 을 조립품으로 돌리면 그것을 만드는 공정이 또 필요해진다 → 신설 공정이 1개 더 는다.

**권고(의견)**: 09시트를 근거로 `FS-7020` 으로 **확정**하고, `bom_line.note` 는 "부모 추정" 이 아니라 `09시트 R43 상위 P/N = FS-7020` 으로 고친다. 설계 직관은 생산기술이 실물로 뒤집기 전까지 근거가 아니다. 뒤집을 때의 절차는 위 4줄이 그대로 체크리스트다.

## 3. 반례·위험 목록 — 체결 공정을 신설한다고 가정했을 때

전부 `probe.py` 로 사본 DB에서 **실행해 확인**했다. 재현: `python docs/4m/prototype/issue3/probe.py` (cwd = 저장소 루트). 원출력 `probe-out.txt`.

### E-1 · `processes` 에 `(product_code, line, seq)` UNIQUE 가 없다 — 중복 seq 가 통과한다 【결함】

**재현** (probe E-1)

```sql
INSERT INTO processes(product_code,op,seq,line,name,ct_sec,kind)
VALUES('BLDC-500W-48V','OP-B88',11,'조립 라인','동력전달부 체결',40,'표준');   -- OP-B90 도 seq=11
SELECT group_concat(op) FROM processes WHERE line='조립 라인' AND seq=11;
```

**실측** `OP-B90,OP-B88` — 통과. `processes` 의 유일한 UNIQUE 는 `(product_code, op)` 뿐이다.

**왜 아픈가**: `queries.listProcesses` (server/db.js:562) 는 `ORDER BY p.line, p.seq, p.op` 다. seq 동률이면 **op 문자열 알파벳순**으로 떨어진다:
`OP-B10 < OP-B100 < OP-B110 < OP-B120 < OP-B20 < OP-B85 < OP-B87 < OP-B88 < OP-B90` — 공정 목록과 분해도 모달(`explodedStages`)의 순서가 실제 공정 순서와 무관해진다.

**기대값**: 조립 라인 seq 는 1..(14+N) 의 **중복·결번 없는 연속 정수**. 부분 유니크 인덱스 추가 권고: `CREATE UNIQUE INDEX ux_proc_seq ON processes(product_code, line, seq)`.

**(정정) 게임 맵 정렬은 seq 를 쓰지 않는다.** `queries.listEquipments` (db.js:428) 는 `SELECT * FROM equipments WHERE hidden = 0` — `ORDER BY` 자체가 없고, 맵 배치는 `equipments.x, y` 로만 결정된다. seq 재번호로 **맵은 움직이지 않는다**. seq 가 보이는 곳은 상태창의 `${proc.seq}번째` 라벨(public/js/app.js:365), 관리자 공정 목록, 분해도 모달뿐이다.

### E-2 · `processes.seq` UPDATE 는 R-22 를 우회한다 — 트리거가 INSERT 에만 걸려 있다 【결함】

**재현** (probe E-2)

```sql
-- 정상 상태(R-22 0건)에서
UPDATE processes SET seq = 99 WHERE op='OP-B88';   -- 완성품 산출 OP-B120(seq 15) 보다 뒤로
SELECT * FROM v_chk_r22_seq;
```

**실측**: UPDATE **통과**. 직후 `v_chk_r22_seq` 4건 —
`BLDC-500W-48V OUT@OP-B120(seq 15) < FS-7010 IN@OP-B88(seq 99)` 외 3건.

**대조군 (E-6)**: 같은 위반을 INSERT 로 만들면 막힌다 —
`INSERT ... process_material(io='IN', line_id=BLDC>FS-7010)` on seq 15 공정 → `R-22: 자식 투입 공정이 부모 산출 공정보다 늦다`.

**결론**: `trg_pm_ins`/`trg_pm_upd` 는 `process_material` 에만 걸려 있고 **`processes` 에는 트리거가 하나도 없다**. 체결 공정 신설은 필연적으로 `seq` 대량 UPDATE 를 부르는데, 그 경로가 무방비다. **재번호 후 `v_chk_r22_seq` 를 반드시 재조회해야 한다**(수용 기준 A-7).

**기대값**: 재번호 트랜잭션 종료 시 `v_chk_r22_seq` 0건. 권고: `processes` 에 `AFTER UPDATE OF seq` 트리거를 추가해 같은 검사를 걸거나, 최소한 적재기가 재번호 직후 뷰를 확인하고 ROLLBACK 한다.

### E-3 · 새 공정에 OUT 행이 없어도 아무도 막지 않는다 — "24공정 전부 OUT 1행" 은 제약이 아니다 【결함】

**재현** (probe E-3)

```sql
INSERT INTO processes(product_code,op,seq,line,name,ct_sec,kind)
VALUES('BLDC-500W-48V','OP-B88',11,'조립 라인','동력전달부 체결',40,'표준');
SELECT COUNT(*) FROM processes p
 WHERE NOT EXISTS (SELECT 1 FROM process_material m WHERE m.process_id=p.id AND m.io='OUT');
```

**실측**: OUT 없는 공정 **1건**. `v_chk_summary` 는 여전히 `D-8 / R-10` 만 낸다 — **점검 뷰 11종 중 이것을 잡는 뷰가 없다.**

**왜 아픈가**: 계획서 §4.3 의 "OUT 24행 = 완성 7 + 상태 17" 은 DDL 제약이 아니라 `server/materials.js` 적재기의 관행이다. 공정을 하나 늘리고 OUT 을 빠뜨리면 그 공정을 통과한 로트는 `state_pm_id` 가 가리킬 곳이 없어 **계보가 끊긴 채 조용히 통과**한다.

**기대값**: 모든 공정이 OUT 정확히 1행. 신규 점검 뷰 권고 —

```sql
CREATE VIEW v_chk_out_row AS
SELECT 'D-20' AS rule, p.op || ' OUT ' || (SELECT COUNT(*) FROM process_material m
         WHERE m.process_id = p.id AND m.io = 'OUT') || '행' AS detail
  FROM processes p
 WHERE (SELECT COUNT(*) FROM process_material m WHERE m.process_id = p.id AND m.io = 'OUT') <> 1;
```

### E-4 · 안 A(단일 공정)는 FS-7020 을 같은 공정에서 만들고 즉시 소비한다 — 수명 0 로트 【결함】

가정한 안 A: `OP-B88 동력전달부 체결` 하나가 IN 8행(대상 8건 전부) + OUT `FS-7020 is_final=1` + OUT `BLDC 상태행` 을 갖는다.

**재현** (probe E-4) — **모든 INSERT 가 통과했다.**

```
[안 A] proc=25 pmIN=54 pmOUT=26 pmOUTfinal=8 parts=59 process_inputs=54 D-8=2 R-10=2 R-22=0
FS-7020 이 같은 공정의 IN 이자 OUT: 1건 — 막는 제약 없음
```

**두 가지가 동시에 깨진다**
1. **수명 0 로트**: `FS-7020` 은 `trace_mode='LOT'` 인 실물 SA(item_id 7). 같은 공정에서 `is_final` OUT 으로 로트가 생기고 같은 공정의 IN 으로 소비된다. 백플러시(계획서 §4.5)는 "실적 신고 시 IN 을 FIFO 로 소비하고 OUT 로트를 만든다" 인데 **IN·OUT 이 같은 공정이면 어느 쪽이 먼저인지 정의되어 있지 않다**. 자기 자신을 먹는 순환이 계보에 생길 수 있다.
2. **한 공정 OUT 2행**: `pmOUT=26` 인데 `proc=25` → OP-B88 만 OUT 2행. E-3 의 신규 뷰 `v_chk_out_row` 가 있었다면 여기서 걸렸을 것이다.

**기대값**: `FS-7020` 을 팬텀으로 내리든(그러면 `bop_link='PHANTOM'` 자동, IN 행 불가 — `trg_pm_ins` 1번 규칙), 별도 조립 공정을 주든 **같은 공정에서 만들고 먹는 구조는 금지**. 신규 점검 뷰 권고 —

```sql
CREATE VIEW v_chk_self_feed AS
SELECT 'D-21' AS rule, p.op || ' : ' || i.pn || ' 를 같은 공정에서 산출하고 투입' AS detail
  FROM process_material o JOIN processes p ON p.id = o.process_id JOIN item i ON i.item_id = o.item_id
 WHERE o.io = 'OUT' AND EXISTS (SELECT 1 FROM process_material m JOIN bom_line l ON l.line_id = m.line_id
        WHERE m.process_id = o.process_id AND m.io = 'IN' AND l.child_item_id = o.item_id);
```

가정한 안 B: `OP-B83 플랜지샤프트 No.2 조립`(OUT `FS-7020` is_final, IN 4건) + `OP-B88 동력전달부 체결`(OUT `BLDC` 상태행, IN 4건).

### E-6 · R-22 트리거는 정방향 INSERT 를 실제로 막는다 【확인】

대조군. seq 15(= `OP-B120` 완성품 OUT 뒤) 공정에 `BLDC > FS-7010` IN 을 넣으면 —
`R-22: 자식 투입 공정이 부모 산출 공정보다 늦다 (seq(child IN) > seq(parent OUT), 같은 라인)` 로 **거부**.
→ **체결 공정은 반드시 `OP-B120` 보다 앞 seq 에 놓여야 한다.** 원천(PDF 단계 순서·JSON DRIVE 위치)이 요구하는 "B87 뒤 · B90 앞" 은 이 제약과 충돌하지 않는다.

### E-7 · `split_pct` — R-10 은 뷰일 뿐, 트리거가 없다 【결함(경미)】

**재현** (probe E-7) — `FS-7020 > OR-7025` 를 두 공정에 50/50 으로 쪼갬.

```
50/50 → R-10: 없음(정상).  process_inputs 의 OR-7025: 49:1.0, 50:1.0   (2 EA 가 1+1 로 분할)
50/60 → R-10: ['FS-7020 > OR-7025 split=110.0 (ASSIGNED)']
```

- 합계 110 이 되는 UPDATE 가 **통과**한다. `process_material.split_pct` 의 CHECK 는 행 단위 `(0,100]` 뿐이고 라인 합계를 보는 트리거는 없다.
- D-8 과의 관계: IN 행이 하나라도 생기면 `bop_status` 는 즉시 `ASSIGNED` → **D-8 은 빠지고 R-10 만 남는다**. 즉 "D-8 이 0 이 됐다" 는 배정이 옳다는 증거가 아니다. **D-8 과 R-10 을 함께 봐야 한다**(수용 기준 A-5·A-6).
- 8건을 단일 공정에 100% 로 붙이면 R-10 도 함께 해소된다(E-4·E-5 실측: R-10 10 → 2).

### E-8 · 맵 좌표 — `equipments(x,y)` 유니크 없음, 존·맵 밖 배치도 통과 【결함】

**현황 실측**

| 항목 | 값 |
|---|---|
| 조립 라인 zone(id 6) rect | `x=0, y=8, w=24, h=8` → 유효 칸 `x 0..23, y 8..15` |
| 맵 크기 | `MAP_W=24, MAP_H=16` (server/index.js:23 · public/js/game.js:5) → `x 0..23, y 0..15` |
| 1행 (y=10) | x = 2, 5, 8, 11, 14, 17, 20 — **7대** (OP-B10~B70) |
| 2행 (y=13) | x = 2, 5, 8, 11, 14, 17, 20 — **7대** (OP-B80·B85·B87·B90·B100·B110·B120) |
| **이미 겹친 칸** | **(11,13) 에 `CNC-01`(hidden=1) 과 `OP-B90`(hidden=0) 두 대** |

**재현** (probe E-8) — 전부 **통과**한다(=DB 가 안 막는다):

```sql
INSERT INTO equipments(zone_id,code,name,x,y,type,op) VALUES(6,'OP-B88','동력전달부 체결기',23,13,'assembly','OP-B88'); -- 존 안: 통과
INSERT INTO equipments(...) VALUES(6,'OP-B89','체결기2',26,13,...);   -- x>23 맵 밖: 통과
INSERT INTO equipments(...) VALUES(6,'OP-B89b','체결기2',2,16,...);   -- y>15 맵/존 밖: 통과
INSERT INTO equipments(...) VALUES(6,'OP-B89c','체결기3',5,13,...);   -- OP-B85 와 같은 칸: 통과
```

방어선은 `server/index.js` 의 `clampInt(x, 0, MAP_W-1)` / `clampInt(y, 0, MAP_H-1)` 뿐이고 **배치 API 경로만** 탄다. SQL 직접 적재(`load_source.py`·마이그레이션 스크립트)는 그냥 들어간다. 좌표 중복을 막는 인덱스는 **없다**.

**step 3 배치 규약의 한계 — 산수**
한 행의 슬롯 = `x ∈ {2,5,8,...,23}` → `floor((23-2)/3)+1 = **8칸**`. 두 행이면 **최대 16대**.

| 신설 공정 수 N | 조립 설비 | 배치 | 판정 |
|---|---|---|---|
| 1 (안 A) | 15 | 8 + 7 (`x=23,y=10` 추가) | **가능** |
| 2 (안 B) | 16 | 8 + 8 (`x=23,y=10`·`x=23,y=13`) | **가능 — 정확히 한계** |
| 3 이상 | 17+ | 9번째는 `x=26` (맵 밖) 또는 `y=16` (존·맵 밖) | **불가. 존 rect 또는 step 을 바꿔야 한다** |

**검증 방법(다음 라운드)**

```sql
-- ① 존 밖 / 맵 밖
SELECT e.code,e.x,e.y FROM equipments e JOIN zones z ON z.id=e.zone_id
 WHERE e.hidden=0 AND (e.x < z.rect_x OR e.x >= z.rect_x+z.rect_w
                    OR e.y < z.rect_y OR e.y >= z.rect_y+z.rect_h
                    OR e.x NOT BETWEEN 0 AND 23 OR e.y NOT BETWEEN 0 AND 15);
-- ② 좌표 충돌 (숨김 포함 · 숨김 제외 둘 다 본다)
SELECT x,y,group_concat(code) FROM equipments GROUP BY x,y HAVING COUNT(*)>1;
SELECT x,y,group_concat(code) FROM equipments WHERE hidden=0 GROUP BY x,y HAVING COUNT(*)>1;
```

**기대값**: ① 0행. ② hidden=0 기준 0행. (숨김 포함 기준은 현재 `(11,13) CNC-01/OP-B90` 1건 — **기존 부채이고 쟁점 3 이 만든 것이 아니다**. 새 설비가 이 목록을 늘리면 안 된다.)

### E-9 · `mat_lot.state_pm_id` 가 OUT 행 재생성으로 조용히 끊긴다 【결함】

**근거 코드**: `server/materials.js:828` (IN 집합 순서가 바뀌면 `DELETE FROM process_material WHERE process_id=? AND io='IN'` 후 재INSERT → **pm_id 가 전부 새로 발급**), `:845` (`keep` 밖 OUT 행 `DELETE`). 그리고 `server/db.js` 어디에도 **`PRAGMA foreign_keys = ON` 이 없다**(grep 확인 — `journal_mode` 와 `table_info` 뿐).

**재현** (probe E-9)

```
PRAGMA foreign_keys = 0
로트 상태 표시: [('GB-TEST-001', 'OP-B85', '완성')]
DELETE FROM process_material WHERE pm_id = <OP-B85 의 OUT>;   -- 통과
삭제 후:      [('GB-TEST-001', 19, None, None)]   ← state_pm_id 19 는 없는 행을 가리킨다
```

**왜 쟁점 3 에서 아픈가**: 체결 공정을 넣으면 인접 공정의 IN 집합 순서가 바뀐다(예: `OP-B90` 의 IN 9행 앞에 새 공정이 끼어 재적재). 그 경로가 `sameOrder=false` 로 떨어지면 pm_id 가 재발급되고, 이미 그 pm_id 를 `state_pm_id` 로 물고 있던 로트는 **상태 표시가 빈칸이 된다**. 지금은 `mat_lot` 0행이라 피해가 없지만(실측), **로트를 넣기 전에 고쳐야 한다**.

**기대값**: dangling 0. 점검 쿼리 —

```sql
SELECT COUNT(*) FROM mat_lot m
 WHERE m.state_pm_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM process_material pm WHERE pm.pm_id = m.state_pm_id);
```

권고: (a) `PRAGMA foreign_keys = ON` 을 켜거나, (b) `state_pm_id` 를 pm_id 대신 `(op, out_state)` 로 잡거나, (c) 최소한 위 쿼리를 `v_chk_*` 로 승격.

**백플러시 지점 5곳(§4.5)에 대한 영향** — 실측 기준 정리

| 지점 | `is_final` OUT | 체결 공정 신설의 영향 |
|---|---|---|
| OP-A100 (SA-1000) | 유지 | 없음 |
| OP-B40 (RA-2000) | 유지 | 없음 |
| OP-B85 (GB-8000) | 유지 | **GB-8000 이 드디어 소비된다** — 지금은 만들고 아무도 안 먹는다 |
| OP-B87 (PL-9000) | 유지 | 위와 같음 |
| OP-B120 (완성품) | 유지 | IN 이 늘지 않는다(체결 공정이 먹으므로) |
| **(신설) 체결 공정** | **상태행(is_final=0)** → 백플러시 지점 **아님** | **여기가 핵심 위험** ↓ |

체결 공정의 OUT 을 `BLDC is_final=0` 상태행으로 두면 백플러시 지점이 **5곳 그대로**다. 그러면 그 공정의 IN 4~8행은 **어느 실적 신고 시점에 소비되는가?** 계획서 §4.5 는 "`is_final` OUT 지점에서 실적 신고 시 그 공정 IN 을 소비" 라고 썼고, 상태행 공정(B50~B80, B90~B110)의 IN 이 어떻게 처리되는지는 **본문에 명시가 없다**. 현행 B50~B80 도 같은 상태이므로 **기존 미정의 규칙이 8건만큼 더 커지는 것**이지 새 결함은 아니다 — 하지만 쟁점 3 을 닫으면서 확인해야 한다. → §5 질문 Q-1.

**(정정) `production_records` 는 seq 재번호의 영향을 받지 않는다.** 실측: `production_records` 는 `work_order_id · equipment_id · user_id` 만 참조하고 `process_id`·`seq` 를 갖지 않는다(DDL 확인). 현재 3행 전부 `equipment_id` = `PRS-01`/`INS-01`(`op` 가 NULL 인 구형 설비)이라 공정과 연결조차 안 돼 있다. 위험은 seq 가 아니라 **설비 행을 지우거나 code 를 바꿀 때** 생긴다 — 인터페이스 §7 의 `hidden=1` 규약을 지키면 된다.

### E-10 · OR-7025 부모 이동 — 삭제가 막히고, 절단 전 상태에서 이중계상 【결함(잠재)】

**재현** (probe E-10)

```
[통과] FS-7010 용 bom_header 신설
[통과] FS-7010 > OR-7025 2 EA 라인 추가
[거부] 기존 FS-7020 > OR-7025 라인 DELETE  -> R-11: 승인된 BOM 의 라인은 삭제하지 않는다 — valid_to 를 끊어라
완성품당 OR-7025 소요량: FS-7020=2.0, FS-7010=2.0     ← 합 4 EA
item_type: PT                                          ← 단품인데 BOM 을 소유
parts 뷰: [('OR-7025','L2','FS-7020')]                 ← 한 줄만. FS-7010 쪽은 화면에서 안 보인다
```

세 가지가 동시에 드러난다.

1. **부모 이동은 ECO + `valid_to` 절단 경로뿐**이다. DELETE 는 R-11 이 막는다. 절차를 모르고 하면 여기서 막힌다.
2. **절단 전 두 라인이 동시 유효하면 완성품당 OR-7025 가 2 → 4 EA 로 뛴다.** 09시트 합계 310.35 도 312.35 로 어긋난다. → 이 대조가 안전망이다(수용 기준 A-9).
3. **`item_type='PT'` 인 품목이 BOM 을 소유해도 아무도 안 막는다.** `v_chk_r5_lost_sa` 는 반대 방향(SA/FG 인데 BOM 없음)만 본다. `FS-7010` 을 조립품으로 돌리려면 `item_type` 을 `SA` 로 바꾸고(그러면 R-5 가 BOM 유무를 감시) 그것을 만드는 공정을 또 만들어야 한다.

### E-11 · `parts` 호환 뷰의 `MIN(line_id)` 중복제거가 다부모를 숨긴다 【결함】

`v_parts_compat` 는 `line_id = (SELECT MIN(line_id) ... WHERE child_item_id = q.child_item_id)` 로 **품목당 한 줄**만 낸다. 그래서:

- 같은 단품이 두 부모 밑에 걸려도 `parts` 는 첫 줄만 보인다 → **설비 상태창·단품 목록에서 이중계상이 안 보인다**.
- 전개 진실은 `v_bom_line_qpp` 에만 있다. **검수는 `parts` 가 아니라 `v_bom_line_qpp` 로 해야 한다.**

**체결 공정 신설 자체는 `parts` 행수를 바꾸지 않는다** — 실측: 안 A·안 B 둘 다 `parts=59` 불변. BOM 라인을 늘리지 않기 때문이다. **따라서 설비 상태창 계약(`equipment:detail.process.inputs[]`)은 깨지지 않는다.** 바뀌는 것은 `process_inputs` 뿐: 46 → **54**.

계약 관점 점검(인터페이스 §7):

| 계약 요소 | 현행 | 신설 후 | 판정 |
|---|---|---|---|
| `parts` 행수 | 59 | **59** | 불변 — 계약 안전 |
| `process_inputs` 행수 | 46 | **54** | 증가. 스키마·키 모양은 그대로 |
| `process_inputs` PK 의미 `(process_id, pn)` | 호환 뷰에는 제약 없음. 실제 유니크는 `ux_pm_in(process_id, line_id) WHERE io='IN'` | 같음 | **같은 pn 이 같은 공정에 두 라인으로 들어오면 뷰가 pn 중복 행을 낸다** — 대상 8건에는 그런 조합이 없다(실측) |
| `inputs[]` 원소 shape | `{pn,name,spec,qty,unit,level,parentPn,parentName,image}` | 같음 | 새 행의 `image` 는 `FS-7021/7022/7023/OR-7025` 파일이 없어 부모 `FS-7020.png` 로 대체(실측) — 인터페이스 §7 규약대로 |
| `stage` 블록 | `stage_pn` 기준 | ↓ E-12 | **깨진다** |

### E-12 · `processes.stage_pn` 이 단일값이라 체결 공정이 DRIVE 4단계를 못 덮는다 【결함】

체결 공정은 분해도 stage 5·6·7·8(FS-7010·FS-7020·GB-8000·PL-9000) **네 단계의 부품을 한 번에** 붙인다. 그런데 `processes.stage_pn` 은 **TEXT 한 칸**이다. 무엇을 넣든 나머지 3단계는 여전히 공정 0건으로 남는다.

**현행 실측** (§1.5): stage 5·6 이 이미 `없음`. 안 A 에서 `stage_pn='FS-7010'` 을 주면 stage 5 만 채워지고 **stage 6 은 여전히 빈다**. 안 B(`OP-B83.stage_pn='FS-7020'`, `OP-B88.stage_pn='FS-7010'`)면 5·6 둘 다 채워진다.

**검증 쿼리**

```sql
-- 분해도 단계 중 공정이 0건인 것
SELECT s.value->>'stage', s.value->>'pn' FROM products p,
       json_each(json_extract(p.spec_json,'$.exploded')) s
 WHERE NOT EXISTS (SELECT 1 FROM processes pr
                    WHERE pr.product_code = p.code AND pr.stage_pn = s.value->>'pn');
```

**현행 실행 결과**: `[(5, 'FS-7010'), (6, 'FS-7020')]` — **2행**. (SQLite 3.50.4, `->>` 연산자 사용 가능 확인)

**기대값**: **0행**. (= 분해도 9단계 전부 공정 ≥1건) 이것이 "체결 공정이 생겼다" 를 화면에서 확인하는 가장 짧은 방법이다.

### E-13 · `bop_link` REQUIRED→ASSIGNED 전환은 스키마 변경이 아니다 【확인】

`bop_link` 컬럼 값은 **바뀌지 않는다**. `REQUIRED` 그대로다. 바뀌는 것은 `v_bom_line_bop.bop_status` 의 계산 결과뿐 —

```sql
CASE WHEN EXISTS (SELECT 1 FROM process_material pm WHERE pm.line_id = q.line_id AND pm.io='IN')
     THEN 'ASSIGNED' ELSE 'UNASSIGNED' END
```

즉 **IN 행을 1건 넣는 순간 파생값이 뒤집힌다**. UPDATE 도 ECO 도 필요 없다. 실측: 안 A·안 B 둘 다 `D-8: 10 → 2`, `R-10: 10 → 2`.

주의: `trg_pm_ins` 1번 규칙이 `bop_link <> 'REQUIRED'` 인 라인의 IN 을 거부한다. 대상 8건은 전부 `REQUIRED` 이므로(실측) 통과한다. 반대로 `FS-7020` 을 **팬텀으로 내리면** `BLDC > FS-7020` 라인이 자동으로 `PHANTOM` 이 되어 **IN 을 못 넣는다** — 그때는 `FS-7020` 의 자식 4개가 체결 공정으로 직접 올라가야 하고 IN 총수가 54 가 아니라 **53**(FS-7020 라인 1건 제외)이 된다. 수용 기준을 안에 맞춰 골라야 한다.

## 4. 수용 기준 — "쟁점 3 이 닫혔다" 고 말하려면

적재 후 이 표의 **기대값이 전부 맞아야** 닫힌 것이다. 다음 라운드에 내가 이 표로 실증한다.
`N` = 신설 조립 공정 수. `F` = FS-7020 전용 조립 공정을 두면 1, 아니면 0 (`F ≤ N`).
`P` = FS-7020 을 팬텀으로 내리면 1, 실물 유지면 0.

| # | 항목 | 확인 방법 | 기대값 |

### F-2 【결함 · 차단】 E-2 는 닫히지 않았다 — 사후 점검이 그 실패를 못 잡는다

결의안 §4.3·§6.1 E-2 의 방어는 **"적용 순서 고정 + `v_chk_r22_seq` 를 뷰로 재조회"** 하나다. 그런데 `v_chk_r22_seq` 는 **부모 OUT vs 자식 IN** 만 본다. 신설 `OP-B89` 의 IN 4건은 부모가 전부 완성품이고 완성품 OUT 은 `OP-B120`(seq 16)이므로, **`OP-B89` 를 seq 1~15 어디로 옮겨도 R-22 는 0 을 유지한다.**

**재현**(`resolution-out.txt` §4)

```
적재 완료 → v_chk_r22_seq = 0
UPDATE processes SET seq = 3 WHERE op = 'OP-B89';    -- 통과 (트리거 없음)
v_chk_r22_seq   = 0 건          ← 초록
v_chk_summary   = D-8 2 · R-10 2  ← 초록
실제 위반 3건:
  FS-7020 소비 OP-B89(seq 3) < 산출 OP-B88(seq 11)
```

윤태경 자신이 §3 (C-1) 에서 *"`v_chk_r22_seq` 가 부모 기준 비교라 자동으로 잡히지 않는다 — 더 나쁘다. 점검 뷰를 통과하는 거짓 데이터가 된다"* 고 적었다. **그 구멍은 (C-1) 안에만 있는 게 아니라 본안에도 그대로 있다.** 본안은 서브조립 3개가 완성품 직하로 들어오는 구조라 오히려 이 축의 노출이 커진다.

**보완 (내가 쓴 정확한 SQL — `docs/4m/prototype/issue3/patch-checks.sql` 에서 실행 확인)**

```sql
-- [R-23] 자식을 만들기 전에 소비한다 — R-22 가 못 보는 축
DROP VIEW IF EXISTS v_chk_make_before_use;
CREATE VIEW v_chk_make_before_use AS
SELECT 'R-23' AS rule,
       ic.pn || ' 투입@' || pc.op || '(seq ' || pc.seq || ') < 산출@' || pm.op || '(seq ' || pm.seq || ')'
       || CASE WHEN pc.line <> pm.line THEN ' [라인 다름 — 수동 확인]' ELSE '' END AS detail
  FROM bom_line l
  JOIN item ic ON ic.item_id = l.child_item_id
  JOIN process_material pi ON pi.line_id = l.line_id AND pi.io = 'IN'
  JOIN processes pc ON pc.id = pi.process_id
  JOIN process_material po ON po.item_id = l.child_item_id AND po.io = 'OUT' AND po.is_final = 1
  JOIN processes pm ON pm.id = po.process_id
 WHERE pc.line = pm.line AND pc.seq < pm.seq;
```

**기대값**: 본안 적용 후 **0행**(실측 0행). 위 seq 3 공격을 넣으면 **3행**(실측 3행). `v_chk_summary` 의 UNION 목록에 이 뷰를 추가해야 콘솔 카드가 빨강이 된다.

**멱등성 주의 — `ddl-v1.sql` 이 매 기동 실행된다는 점과 직결된다.** `ddl-v1.sql` 은 뷰를 전부 `CREATE VIEW IF NOT EXISTS` 로 만든다. **이미 배포된 DB 에서는 뷰 정의를 고쳐도 조용히 무시된다.** 실증(`resolution-out.txt` §5d, 판정 `V-1`): 기존 `v_chk_bop_unassigned` 에 `IF NOT EXISTS` 로 새 정의를 실행했더니 **옛 정의가 그대로** 돌았다. 따라서 `v_chk_summary` 처럼 **본문을 고쳐야 하는 뷰는 `DROP VIEW IF EXISTS` → `CREATE VIEW` 쌍으로 써야 한다**(뷰에는 데이터가 없으므로 DROP 이 안전하다. 테이블·인덱스는 `IF NOT EXISTS` 유지). → 조건 C-6.

**선택 보강 — seq UPDATE 트리거.** `docs/4m/prototype/issue3/patch-seq-trigger.sql` 에 `trg_proc_seq_upd`(BEFORE UPDATE OF seq, line ON processes, R-22 양방향 + R-23) 를 써서 시험했다.

| 시험 | 결과 |
|---|---|
| 트리거를 건 채 **결의안의 정상 재번호**(배열 순서 = 오름차순 UPSERT) | **통과** (T-1) — 정상 작업을 막지 않는다 |
| 트리거를 건 채 적재 후 `v_chk_r22_seq` | 0 (T-2) |
| E-2 공격 ①: `OP-B89` → seq 3 | **거부** `R-23(seq): 만들기 전에 소비하는 자재가 생긴다` (T-3) |
| E-2 공격 ②: `OP-B89` → seq 99 | **거부** `R-22(seq): 이 공정의 투입이 부모 산출 공정보다 늦어진다` (T-4) |
| `UPDATE … SET seq = seq + 10 WHERE seq >= 5` (대량, 중간 상태 어긋남) | **거부** — 순서 보존 변환인데도 막힌다 |
| 같은 +10 을 **내림차순 1행씩** | **통과** |

→ **트리거는 유효하지만 행 단위라 "중간 상태" 를 허용하지 않는다.** 도입한다면 *"상향 재번호는 seq 내림차순으로 1행씩"* 을 적용 절차에 못 박아야 한다. 이번 결의안의 재번호는 그대로도 통과하므로(T-1) **뷰(R-23)를 필수 조건으로, 트리거는 선택**으로 둔다.

> **부수 발견** — R-22 의 앵커는 "부모의 `is_final` OUT" 인데, **팬텀 부모에는 OUT 행이 없다**(`V12-7` 이 금지). 조립 라인 IN 46행 중 **20행이 팬텀 부모**다(`HA-3000` 7 · `PE-6000` 10 · `EX-5000` 3). 즉 그 20행의 투입 순서는 **아무 규칙도 안 탄다**. 본안이 만드는 문제는 아니지만, R-22 를 "순서가 지켜진다는 증거" 로 읽으면 안 된다는 뜻이다. (`seq+3` 대량 UPDATE 가 트리거를 통과한 것도 이 때문이다 — 걸릴 앵커가 없었다.)

### F-3 【결함 · 차단】 E-3 은 닫히지 않았다 — 그리고 `expected` 대조는 커밋을 막지 않는다

그런데 그 유일한 감지가 **커밋을 막지 못한다**:

즉 **콘솔 "제품 라인 적용" 버튼으로는 `expected` 가 어긋나도 트랜잭션이 커밋되고 경고 한 줄만 남는다.** 결의안 §8 의 *"5. 어긋나면 커밋하지 않는다"* 는 **git 커밋을 안 한다는 뜻일 뿐, DB 는 이미 쓰였다.** 그리고 그 DB 를 되돌리려면 §7 5·6번의 명시 DELETE 가 필요하고, 그게 바로 E-9 경로다.

**보완 1 (점검 뷰 — 실행 확인)**

```sql
-- [D-9] 공정당 산출(OUT) 행 정확히 1행
DROP VIEW IF EXISTS v_chk_proc_no_out;
CREATE VIEW v_chk_proc_no_out AS
SELECT 'D-9' AS rule,
       p.op || ' ' || COALESCE(p.name,'') || ' — OUT ' ||
       (SELECT COUNT(*) FROM process_material m WHERE m.process_id = p.id AND m.io = 'OUT') || '행' AS detail
  FROM processes p
 WHERE (SELECT COUNT(*) FROM process_material m WHERE m.process_id = p.id AND m.io = 'OUT') <> 1;
```

**기대값**: 본안 적용 후 **0행**(실측 0행). OUT 을 빠뜨린 반례에서 `"OP-B89 동력전달부 체결 — OUT 0행"` **1행**(실측 확인).

**보완 2 (적재기 단정)**: `apply-sample` 이 `strict: true` 로 부르도록 하거나(`server/index.js:535` — 최민준 소관), 최소한 `expectedMatch === false` 면 **HTTP 400 으로 실패시키고 롤백**해야 한다. 지금은 200 OK 에 `warnings[]` 한 줄이다.

### F-4 【결함 · 경미】 §6 의 전제 "`bom_header`·`bom_line`·`item` 에 INSERT/UPDATE/DELETE 가 하나도 없다" 는 거짓이다

적재기 5단계는 **매 실행 `bom_line` 59행 전부에** `UPDATE bom_line SET line_no, qty_per, uom_code, qty_basis, scrap_pct, note` 를 건다(`server/materials.js:225`). 그리고 결의안 §4.4(d) 는 **의도적으로** `line_attrs` note 3건을 고쳐 쓴다.

**재현**(`resolution-out.txt` §5c): 적재 후 `note` 가 실제로 바뀐 행 = **`line_id` 46·47·48 3건**(`FS-7020>FS-7021·FS-7022·OR-7025`). 행수는 59 → 59 불변.

해가 되는 변경은 아니다(`bom_line.note` 에는 트리거가 없다 — `ddl-v1.sql` 의 `bom_line` UPDATE 트리거는 `child_item_id`·`uom_code`·`qty_per`·`bop_link`·`valid_*` 컬럼에만 걸린다). 그러나 §6 전체가 이 전제 위에 R-1·R-2·R-4·R-5·R-12 를 "무변경이므로 0" 이라고 논증하므로, **전제 문장이 틀리면 논증의 형태가 틀린다**. 정확한 문장은 *"`bom_line` 의 **구조 컬럼**(`bom_id`·`child_item_id`·`qty_per`·`uom_code`·`valid_from`·`bop_link`)이 바뀌지 않는다. 바뀌는 것은 `note` 3건뿐이다"* 다. (결론 자체는 실측으로 맞다 — R-1·R-2·R-4·R-5·R-12 전부 0.)

### F-5 【결함 · 경미】 §6 트리거표의 R-22(OUT) 근거가 틀렸다

결의안 §6 트리거 표: *"`R-22` OUT(is_final) 뒤에 늦은 IN 라인 금지 | **적재 순서가 OUT 26행 → IN 54행이라 OUT 삽입 시점에 해당 IN 이 아직 없다** ✓"*.

이 근거는 **빈 DB 에서만 참**이다. 이미 적재된 운영 DB 에 다시 적재하면 OUT 은 INSERT 가 아니라 **UPDATE** 로 가고(`server/materials.js:241`), 그 UPDATE 는 `is_final` 을 포함하므로 **`trg_pm_upd` 가 뜬다**(`ddl-v1.sql:544` — `BEFORE UPDATE OF process_id, io, line_id, item_id, is_final`). 그때 IN 54행은 **이미 전부 존재한다.** 결과적으로 통과하는 이유는 "IN 이 없어서" 가 아니라 **"seq 순서가 실제로 맞아서"** 다. A-21(2회차 재적재)이 통과한 것이 그 증거다. 결론은 맞고 **근거만 정정하면 된다** — 그런데 이 근거를 믿으면 *"순서가 틀려도 첫 적재는 통과한다"* 는 잘못된 안심으로 이어질 수 있다.

### F-6 【의견】 §4.7 에서 내 1라운드 실측을 잘못 인용했다

*"535 는 두 신설 공정에 **25+45** 를 넣은 경우다"* → 실제 `probe.py` 는 `OP-B83` **30초** · `OP-B88` **40초**(30+40)였다. 합은 같아 결론에 영향은 없다. 원출력은 `probe.py` 46·62행.

## 7.6 C/T 25초 / 40초 판정

**판정: 값 자체는 수용. 표기 방식은 결함.**

**수용하는 이유** — 세 가지가 실측으로 맞다.

1. **제약을 넘지 않는다.** 실측 MAX C/T = 60.0(`OP-B90`·`OP-B110` **동률**). 25·40 둘 다 60 미만이므로 병목·UPH 60·일 1020대 불변(A-20 통과). `OP-B89` 의 여유는 **20초**, `OP-B88` 은 **35초**다.
2. **유추 근거가 원천 안에 있다.** `OP-B87` 파킹락(부품 4종) 25초 ↔ `OP-B88`(부품 4종) 25초. `OP-B80`(3종) 30초 < `OP-B89` 40초 < `OP-B85`(5종) 50초. 지어낸 수치가 아니라 **같은 라인의 이웃값에서 보간한 값**이다.
3. **대안이 없다.** 원천 xlsx·JSON·PDF 어디에도 이 두 공정의 C/T 가 없다(1라운드 U-1). 값을 비워 두면 `ct_sec` 가 NULL 이 되어 `SUM`·라인밸런스 계산이 깨진다.

**표기가 결함인 이유** — **잠정값이라는 사실이 기계가 읽는 자리에 없다.**

| 자리 | 잠정 표시 | 판정 |
|---|---|---|
| `bldc-500w-48v.json` `processes[].note` | `"… C/T·QC 는 잠정(생산기술 실측 전)"` 문자열 | 사람만 읽는다 |

2. `cleansing-v1.json` 의 `pm_decisions_pending` 에 **`"3b": "OP-B88·OP-B89 C/T·QC 실측 — 생산기술"`** 을 남긴다. §4.4(g) 는 3번을 통째로 `pm_decisions_closed` 로 옮기는데, **C/T·QC 는 아직 안 닫혔다.** 3번 전체를 닫으면 이 항목이 사라진다.
3. **라인 밸런스 병목 동률을 먼저 기록한다.** `lineBalance."조립 라인"` 은 병목을 `OP-B110` 하나로 적고 있으나 **`OP-B90` 도 60.0초**다(실측). 같은 블록의 `"목표 대비 달성률": "0"` 도 틀렸다(UPH 60 = 목표 60 → 100%). 이건 1라운드 C-4 로 이미 올린 원천 결함인데 **결의안이 이어받지 않았다.** 신설 공정의 C/T 여유(20초)를 논하려면 **천장이 두 개라는 사실이 먼저 기록되어야 한다.**
