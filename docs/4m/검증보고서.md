| 단위 | 건수 | 품목 | 환산 정의 |
|---|---:|---|---|
| `EA` | 41 | (대부분) | 기준 |
| `g` | 5 | `MW-1030`(180) `IV-1070`(15) `AD-2040`(0.5) `SP-4040`(0.5) `GB-8050`(25) | kg↔g 미정의 |
| `kg` | 1 | `SC-1011`(0.85) | **같은 라인에 g 와 kg 이 공존** |

- `EX-5000` 은 `SET` 인데 구성이 `HA-3000/EX-5000` 로 잘못 붙어 있어 **한 세트가 몇 EA 인지 알 수 없다.**

## 1.5 수량 분포

| 항목 | 값 |
|---|---|
| 최소 / 최대 | 0.5 / 180.0 |
| 0 이하 | **0건** (확인) |
| 음수 | **0건** (확인) |
| NULL | **0건** (확인) |
| 소수 | **4건** — `SC-1011` 0.85 kg · `LC-1080` 0.5 m · `AD-2040` 0.5 g · `SP-4040` 0.5 g |
| `qty_per_parent` ≠ `qty_per_product` | 0건 (모든 `parentPerProduct` = 1.0) |

수량 자체는 깨끗하다. 다만 **소수 4건에 대한 반올림·최소포장 정책이 없고**,
모든 서브어셈블리가 완성품당 1개라서 **다단계 수량 곱셈(a×b, b≠1)이 실데이터로 검증된 적이 없다.**
b≠1 인 사례가 없다는 것은 전개 로직의 가장 중요한 부분이 **미검증**이라는 뜻이다. → TC-11

## 1.6 공정 ↔ 자재 연결

| 항목 | 값 |
|---|---|
| 공정 수 | 24 (아마추어 10 · 조립 14) |
| 공정-자재 투입 | 36건 |
| **투입 자재 0건인 공정** | **7건** — `OP-A20` `OP-A50` `OP-A70` `OP-A90` `OP-A100` `OP-B30` `OP-B110` |
| 투입 1건 / 2건 / 3건 / 4건 / 5건 공정 | 7 / 4 / 4 / 1 / 1 |
| **어느 공정에도 투입 안 되는 품목** | **20건** (DB 기준) |
| 설비 ↔ 공정 연결 | 24 / 24 (확인, 누락 없음) |
| `op` 중복 설비 | 0건 (확인) |

**투입 안 되는 품목 20건**
`BB-4070 CP-4050 EX-5000 FS-7010 FS-7020 FS-7021 FS-7022 GB-8000 GD-4040 HA-3000 HK-4060 HS-4020 IP-1040 LC-1080 MO-4030 OR-7025 PC-4010 PC-4011 PL-9000 SP-4040`

- `PE-6000` 의 구성품 10개 중 **8개가 BOP에 없다** — `OP-B90` 이 `PE-6000`(어셈블리) 하나만 투입받기 때문.
- `GB-8000` `PL-9000` `HA-3000` `EX-5000` `FS-7010` `FS-7020` — **만들기만 하고 완성품에 투입되는 공정이 없다.**
- 단위가 특이한 품목(`IP-1040` 매, `LC-1080` m, `SP-4040` g)이 **전부** BOP에 안 붙었다.

**BOP 레벨 혼재 3건** — `SA-1000`(OP-B50) · `RA-2000`(OP-B70) · `PE-6000`(OP-B90) 은
**어셈블리로도 투입되고 그 구성품도 따로 투입된다.** `process_inputs.qty` 를 단순 합산하면 이중 계상이다:

| | EA | g | kg | 매 | m |
|---|---:|---:|---:|---:|---:|
| `process_inputs` 단순합 | **51** | 220.5 | 0.85 | **0** | **0** |
| 엑셀 09 수기 기대값 | **76** | 221 | 0.85 | **12** | **0.5** |

BOP 합계는 BOM 합계와 **어느 단위에서도 맞지 않는다.**

## 1.7 원천 대조표 (엑셀 03~09 ↔ JSON ↔ 운영 DB)

### (1) 03 시트(L1) ↔ JSON `subassemblies` — **9건 전부 일치 (확인)**
P/N · 품명 · 수량 · 단위 모두 일치. 누락·중복 없음.

### (2) 09 시트(평면 통합) ↔ JSON `parts` — **49건 전부 일치 (확인)**
`level` `parentPn` `qtyPerParent` `qtyPerProduct` `unit` `name` **불일치 0건.**
09 시트 49행 = JSON 49행, 양쪽 모두 P/N 중복 없음.
→ **JSON 추출은 정확하다. 오류는 엑셀 09 시트 자체에 있다.**

### (3) 04~08 시트(부모별 상세) ↔ 09 시트(평면) — **수량·단위·레벨 불일치 0건, 그러나 부모가 어긋난다**

| 시트 | A1 제목 | **B2 `상위 P/N`** | F2 `완성품당 SET` | 데이터 행 | 09 시트의 부모 칸 |
|---|---|---|---:|---:|---|
| 04_Stator | Stator Assy (SA-1000) | `SA-1000` | 1 | 10 | `SA-1000` ✅ |
| 05_Rotor | Rotor Assy (RA-2000) | `RA-2000` | 1 | 5 | `RA-2000` ✅ |
| **06_Housing** | Housing **& External (HA-3000/EX-5000)** | **`HA-3000`** | 1 | 10 | **`HA-3000/EX-5000`** ❌ 10건 |
| 07_PE | Power Electronics (PE-6000) | `PE-6000` | 1 | 10 | `PE-6000` ✅ |
| **08_Drive** | Drive Train (Shaft/Gearbox/Parking Lock) | **`FS-7010 / FS-7020 / GB-8000 / PL-9000`** | **4** | 14 | 계열별로 흩어짐 |

04~08 합계 49행 · 유니크 P/N 49 · 내부 중복 0 · 09 시트와 **품목 집합 완전 일치**.
**차이는 오직 "부모가 누구냐" 한 곳에서만 난다.** 06 시트는 B2 에 올바른 부모(`HA-3000`)를 갖고 있는데,
09 시트가 **A1 제목 문자열을 부모 칸에 복사**해 `HA-3000/EX-5000` 가 되었다.

### (4) JSON ↔ 운영 DB — **2건 병합 소실**

| P/N | JSON | 운영 DB | 결과 |
|---|---|---|---|
| `FS-7010` | L1 어셈블리 1행 + L2 단품 1행(동일 품명) | **L1 1행으로 병합** | 관계 1건 소실, 자식 0 |
| `FS-7020` | L1 "Flange Shaft No.2 **Assy**" + L2 "**Flange Base**" | **L1 1행으로 병합**<br>`name`='…Assy' + `spec`='AL 다이캐스트' | **단품 "Flange Base" 소실**<br>이름은 어셈블리, 규격은 단품 — 섞였다 |

인터페이스 §7 의 "단품의 규격은 보존" 은 지켜졌지만, **품명은 어셈블리 쪽이 이겨 한 행에 두 물건이 섞였다.**

# §2. 검증 계획 · 테스트 케이스

## 2.1 판정 기준 (공통)

| 판정 | 뜻 |
|---|---|
| **PASS** | 기대 결과와 **완전히** 일치. 부분 일치는 FAIL |
| **FAIL** | 불일치. 재현 절차 · 실제값 · 기대값을 반드시 기록 |
| **BLOCKED** | 스키마·데이터가 없어 실행 불가 → **미실시**로 남기고 추정하지 않는다 |

- 수치 비교 허용 오차: **1e-9** (부동소수 오차만 허용, 반올림은 불가)
- "막는다"의 정의: **DDL 제약 · 트리거 · 적재 스크립트 검증 중 어디서든 거부되고 오류가 보고**되면 PASS.
  경고만 찍고 데이터가 들어가면 **FAIL** 이다.
- 각 케이스의 `현재` 열은 **이번 라운드에 이미 돌려 본 결과**다 (프로토타입 기준).

## 2.3 DDL 로 막히는 것 / 못 막는 것 (실측)

제약을 건 스키마(`selftest.py` 의 `STRICT_DDL`)에 반례를 하나씩 넣어 확인했다.

| DDL 만으로 **차단됨** (9) | **못 막음** — 트리거·배치·화면 검사 필요 (4) |
|---|---|
| 자기 참조 (`CHECK parent<>child`) | **2단계 이상 순환** `A→B→A` |
| 한 칸에 부모 둘 (`CHECK NOT LIKE '%/%'`) | **유효일자 겹침** (시작일이 다르면 UNIQUE 무력) |
| 수량 0 · 음수 (`CHECK qty>0`) | **대체품 동시 유효** |
| 수량 NULL (`NOT NULL`) | **같은 P/N 단위 불일치** (다른 자리) |
| 부모·자식 미존재 (`FK → items`) | |
| 미등록 단위 (`FK → uom`) | |
| 유효기간 역전 (`CHECK to>=from`) | |
| 같은 시작일 중복 자식 (`UNIQUE`) | |

**오른쪽 4개를 설계에 넣지 않으면 데이터는 반드시 오염된다.** 현행 `parts` 는 왼쪽 9개도 하나도 없다.

### ⚠ V-1 조기 검증 결과 — **동작한다. 단, 순환 길이 12 이상을 놓친다**

초안 §6 R-1 트리거를 **원문 그대로** 임시 SQLite(3.50.4)에 올려 시험했다.

| 확인 | 결과 |
|---|---|
| `CREATE TRIGGER` 성립 (트리거 본문 안의 `WITH RECURSIVE`) | **OK** — SQLite가 받아들인다 |
| CTE 안에서 `NEW.child_item_id` 참조 | **OK** — 상관참조 동작 |
| 자기 참조 `A→A` (= `FS-7010` 사례) | **차단 OK** |
| 순환 길이 2 ~ 11 | **전부 차단 OK** |
| **순환 길이 12 이상** | **통과 — 막지 못한다** |
| 거짓양성 (정상 자식 INSERT) | **없음** |
| INSERT 지연 | **행당 0.354 ms** (1,999행 체인 적재 708 ms) — 허용 범위 |

**결함 D-1** — `WHERE d.depth < 10` 가드가 **탐지 한계를 11로 만든다.**
길이 12 이상 순환은 조용히 통과한다. 더 나쁜 것은 **메시지가 거짓**이라는 점이다:
`RAISE(ABORT, 'BOM 순환 참조 또는 레벨 초과')` 라고 적혀 있지만 **레벨 초과로는 한 번도 raise 되지 않는다.**
깊이 한계에 닿으면 raise 하는 게 아니라 **탐색을 포기**한다.

> 재현: `python docs/4m/prototype/trigger_test.py`
> 품목 12개를 `1→2→…→12` 로 잇고 `12→1` 을 INSERT → **통과**. 11개까지는 차단된다.

BLDC 현행 깊이는 2라 당장은 문제가 없다. 그러나 계획서가 `bom_line.level` 최대 10을
전제한다면 **한계값과 가드값이 같아서 경계가 정확히 취약**하다.

**보완 요구 (R-16)** — 다음 중 하나:
(a) 깊이 한계 도달 시 **별도로 `RAISE`** 해서 "레벨 초과"를 실제로 강제하거나,
(b) 가드를 최대 레벨보다 **충분히 크게** 잡고(예: 64) 깊이 초과는 별도 CHECK 로 잡거나,
(c) 트리거는 그대로 두고 **주기적 전체 그래프 순환 검사**(`bomkit.detect_cycles`)를 이행·야간 배치에 넣는다.
→ 다음 라운드 TC-02 를 **길이 2·11·12·20** 네 가지로 나눠 재시험한다.

### ⚠ V-2 조기 검증 결과 — 인덱스는 동작. 그러나 **R-9가 NULL에서 뚫린다**

| 확인 | 결과 |
|---|---|
| `ux_bom_line_dup` 식 인덱스(`COALESCE(alt_group,'-')`) 생성 | **OK** |
| 같은 `(bom, child, NULL그룹, 같은 시작일)` 2번째 INSERT | **차단 OK** |
| 시작일이 다른 중복 | 통과 (→ R-9 트리거 몫, **역할 분담은 맞다**) |
| 대체그룹만 다른 행 | 통과 (의도대로) |

R-9(유효일자 겹침) 트리거를 원문 그대로 시험한 결과:

| 사례 | 기대 | 실제 |
|---|---|---|
| 둘 다 날짜 있음 · 겹침 (`01-01~06-30` vs `06-01~12-31`) | 차단 | **차단 OK** |
| 둘 다 날짜 있음 · 안 겹침 | 통과 | 통과 OK |
| 기존 행 `valid_to = NULL` | 차단 | **통과 — 뚫림** |
| 신규 행 `valid_to = NULL` | 차단 | **통과 — 뚫림** |
| 둘 다 `valid_to = NULL` | 차단 | **통과 — 뚫림** |

**결함 D-2** — R-9 의 `NEW.valid_from <= x.valid_to AND NEW.valid_to >= x.valid_from` 은
**SQL 3값 논리**에서 한쪽이 NULL 이면 결과가 NULL 이 되고, `EXISTS` 는 거짓이 된다.
즉 **"종료일 미정(NULL)" 인 현행 유효 라인은 겹침 검사를 통째로 빠져나간다.**
현업 BOM 에서 종료일 미정이 **가장 흔한 상태**라는 점에서 실사용 시 거의 상시 무력화된다.

**보완 요구 (R-17)** — 둘 중 하나:
(a) `valid_to NOT NULL DEFAULT '9999-12-31'` 로 **NULL 자체를 없애거나**,
(b) 트리거를 `COALESCE(x.valid_to,'9999-12-31')` · `COALESCE(NEW.valid_to,'9999-12-31')` 로 감싼다.
(a)를 권한다 — 조회·전개 쿼리 전부가 같은 함정을 갖기 때문이다
(`bomkit.as_of_edges` 는 NULL 을 무한대로 해석하도록 이미 그렇게 짜 두었다).

## §5.2 [1] 계획서 §5·§6 DDL 을 원문 그대로 올린 결과

`ddl_v09_raw.sql` 에 §5.1~§5.7 DDL 과 §6 트리거 2개를 **한 글자도 고치지 않고** 옮겼다.
문(statement) 경계는 내 파서가 아니라 **SQLite 자신의 `sqlite3_complete()`** 로 판정했다.

**결과: 25문 중 24문 성공, 1문 실패. 원문 그대로는 실행되지 않는다.**

```
[FAIL] ddl_v09_raw.sql L18  CREATE TABLE uom_conv
       OperationalError: expressions prohibited in PRIMARY KEY and UNIQUE constraints
```

| | |
|---|---|
| 위치 | 계획서 §5.1 `uom_conv` — `PRIMARY KEY (from_uom, to_uom, COALESCE(item_id, 0))` |
| 원인 | SQLite 는 **테이블 제약(PRIMARY KEY / UNIQUE)에 식(expression)을 쓸 수 없다.** 식은 **인덱스**에만 쓸 수 있다 |
| 두 런타임 | python sqlite3 3.50.4 · node:sqlite 3.53.0 **둘 다 같은 메시지로 거부.** 런타임 문제가 아니라 문법 문제다 |
| 대안 | 계획서가 `ux_bom_line_dup` 에서 이미 쓴 바로 그 방법 — 제약을 빼고 식 인덱스로 옮긴다 |

```sql
CREATE TABLE uom_conv (
  from_uom TEXT NOT NULL REFERENCES uom(uom_code),
  to_uom   TEXT NOT NULL REFERENCES uom(uom_code),
  factor   REAL NOT NULL CHECK (factor > 0),
  item_id  INTEGER REFERENCES item(item_id)
);
CREATE UNIQUE INDEX ux_uom_conv ON uom_conv(from_uom, to_uom, COALESCE(item_id, 0));
```

> `item_id` 를 그냥 `PRIMARY KEY (from_uom,to_uom,item_id)` 로 바꾸면 **안 된다.**

> 식 인덱스로 가야 `COALESCE` 의 의도가 지켜진다. (TC-56d 로 확인: 2번째 전역 환산이 거부된다)

### V-1 답: **동작한다. 설계를 후퇴시킬 필요는 없다. 그러나 지금 초안대로 쓰면 순환의 상당 부분을 놓친다.**

윤태경이 물은 것은 "SQLite 트리거 본문의 `WITH RECURSIVE` 가 동작하는가" 다. **동작한다.**
`CREATE TRIGGER` 도 성립하고, CTE 안에서 `NEW.child_item_id` 를 참조하는 것도 되고, 지연은 무시할 수준이다
(1만 품목·1만 라인 일괄 적재에서 라인당 **0.005 ms**, 전체 57 ms). 적재 계층 검사로 후퇴할 이유가 없다.

문제는 **동작 여부가 아니라 적용 범위**다. 결함 4건 중 **D-3 이 가장 위험하다.**

> `bom_header.status` 의 기본값은 `'DRAFT'` 다(§5.4).
> R-1 트리거의 CTE 는 `h.status IN ('APPROVED','ACTIVE')` 로 전개한다.
> **즉 새로 만든 BOM 은 전부 DRAFT 이고, DRAFT 사이의 순환은 전혀 탐지되지 않는다.**
> 이행 [1] 병행 적재가 바로 그 상태다. **순환 차단이 가장 필요한 순간에 꺼져 있다.**

자기참조(`A→A`)만 예외적으로 잡힌다 — CTE 의 `depth=0` 시드가 `bom_header` 를 거치지 않기 때문이다.
그래서 "`FS-7010 → FS-7010` 이 ABORT 된다"는 초안의 기대값은 **맞지만, 그 성공이 나머지를 가린다.**

**제안 (D-3·D-4·D-5·D-1 을 한 번에)**

```sql
-- ① 상태 필터를 뺀다. 구조 무결성은 승인 상태와 무관하다.
--    "DRAFT 니까 순환이어도 된다" 는 성립하지 않는다 — 승인하는 순간 순환이 된다.
-- ② 깊이 가드를 '탐색 포기'가 아니라 '레벨 초과 RAISE'로 바꾼다.
-- ③ 같은 트리거를 UPDATE OF bom_id, child_item_id 에도 건다.
CREATE TRIGGER trg_bom_line_cycle_ins BEFORE INSERT ON bom_line
BEGIN
  SELECT RAISE(ABORT, 'BOM 순환 참조 또는 레벨 초과')
  WHERE EXISTS (
    WITH RECURSIVE down(item_id, depth) AS (
      SELECT NEW.child_item_id, 0
      UNION ALL
      SELECT l.child_item_id, d.depth + 1
        FROM down d
        JOIN bom_header h ON h.parent_item_id = d.item_id
                         AND h.status <> 'OBSOLETE'        -- ① DRAFT 도 본다
        JOIN bom_line   l ON l.bom_id = h.bom_id
       WHERE d.depth < 64                                  -- ② 실용상 무한. 레벨 10 은 별도 규칙으로
    )
    SELECT 1 FROM down
     WHERE item_id = (SELECT parent_item_id FROM bom_header WHERE bom_id = NEW.bom_id)
        OR depth >= 64                                     -- ② 한계 도달도 raise
  );
END;
-- ③ UPDATE 용 동일 트리거 (초안에 '추가한다'고만 적혀 있고 코드가 없다)
CREATE TRIGGER trg_bom_line_cycle_upd
  BEFORE UPDATE OF bom_id, child_item_id ON bom_line BEGIN ... 같은 본문 ... END;
```

`depth < 64` 로 올려도 비용은 걱정 없다 — 위 V-1h 측정이 근거다.
**"최대 레벨 10"(R-2)은 순환 트리거가 아니라 별도 점검 쿼리로 분리하라.** 지금은 한 문장이 두 일을 하려다 둘 다 놓친다.

계획서 §3.3 시나리오를 그대로 넣고 양방향으로 돌렸다. **둘 다 끝까지 도달한다.**

`lot_genealogy` 한 행에 자재·공정·설비·작업자·실적이 같이 들어간다 — **4M 이 여기서 만난다는 §5.6 의 주장은 사실이다.**

1. "OP-A80 함침 배치 #7 에 들어간 스테이터 30개를 대라" → **배치를 묶는 로트가 없다.**

3. "완성품 1대에 들어간 BT-3070 볼트 8개의 로트" → BULK 출고 품목은 계보 행을 만들 근거가 없다(D-18).

## §5.10 사용자 3대 요구 충족 판정

PM 이 2026-09-12 에 정한 요구 3가지에 대한 정면 판정이다.

### ① 제품자재를 BOM 과 BOP 에 넣을 수 있는 구조인가 — **조건부 충족**

**넣었다.** BLDC 실데이터 60품목·59라인·BOP 56행이 **막힌 행 0건**으로 들어갔고, 계획서 §5.8 의 행 수 예상과 전부 일치했다.
`bom_line` ↔ `process_material` N:M 연결이 성립하고, 24공정 전수 매핑이 목록으로 나온다.
현행 `parts.parent_pn` 이 표현하지 못하던 다대다·다단계·팬텀이 전부 표현된다.

**그러나 아직 운영에 못 올린다.**
- DDL 이 **원문 그대로는 실행되지 않는다**(D-19).
- 59 라인 중 **11 이 공정에 안 붙고**, 그 11 이 "팬텀"인지 "미배정"인지 **DB 가 구분하지 못한다**(D-8).
- **공정별 소요량을 내는 공식과 쿼리가 계획서에 없다**(D-21) — BOM↔BOP 를 이었는데 그 위에서 계산할 규칙이 비어 있다.
- 기존 화면을 지키기로 한 **호환 뷰가 §10.3 계약을 깬다**(D-10).

### ② 모자관계(부모-자식)가 데이터로 강제되는가 — **부분 충족. 아직 "강제된다"고 말할 수 없다**

반례 **31건**을 실제로 넣어 봤다. **15건 차단 · 16건 통과**(§5.6 끝 표).

**강제되는 것 15건** — 전부 DDL 의 `CHECK`·`FK`·`UNIQUE` 가 잡았다: 부모·자식 양쪽 FK(`item_id`), 자기참조,
ACTIVE 구간의 순환(길이 11까지), 중복 자식, 기간 겹침(INSERT), `qty_per` 0·음수, `scrap_pct` 범위,
`base_qty` 0, 단위 코드, 복합 부모(구조적으로 표현 불가).

**뚫리는 것 16건** — 전부 "트리거로 하겠다"·"적재 계층에서 하겠다"고 적고 **코드가 없는 자리**다:
**DRAFT 구간의 모든 순환**(= 적재 중 상태), 길이 12 이상 순환, **UPDATE 전 경로 전부**,
`valid_to < valid_from`, `bom_header` 리비전 겹침, 단위 정합·소수 자릿수, 대체 그룹, **로트 계보 무결성 전부**.

> 가장 뼈아픈 것은 **D-3** 이다. `status` 기본값이 `DRAFT` 이므로 **이행 [1] 병행 적재 구간 내내 순환 차단이 꺼져 있다.**
> 현행 데이터에 실제로 자기참조가 2건 들어와 있는 시스템이다. 그 데이터를 옮기는 바로 그 순간에 방어가 없다.
> **이 한 줄(`h.status IN (...)`)만 고치면 ②의 판정이 크게 달라진다.**

### ③ 트리로 성립하는가 — **충족. 단 "성립한다"이지 "유지된다"가 아니다**

| 검산 | 결과 |
|---|---|
| 노드 − 간선 = 1 | **60 − 59 = 1** ✅ (계획서 §3.2 검산과 일치) |
| 순환 | **0건** ✅ (현행 자기참조 2건 → 0) |
| 단일 루트 | **1개** (`BLDC-500W-48V`) ✅ |
| 고아 품목(R-4) | **0건** ✅ |
| 미아 조립품(R-5) | **0건** ✅ (`FS-7010` 단품 재분류로 해소) |
| 루트에서 도달 불가 | **0건** ✅ |
| 최대 깊이 | **4** (L0~L4) ✅ |
| 다부모(공용 부품) 표현 | 주입 시 역전개가 **상위 경로 2개 전부** 출력 ✅ |

**트리로 성립한다. 세 요구 중 ③ 만은 이견 없이 충족이다.**

> 다만 이 등식은 **적재 결과**이지 **제약**이 아니다. D-3·D-5 때문에 내일 누가 UPDATE 한 번으로 깨뜨려도 DB 가 막지 않는다.
> "트리로 성립한다"와 "트리로 유지된다"는 다른 말이다. **②를 고쳐야 ③이 지속된다.**
