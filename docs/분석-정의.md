# 실적 분석 지표 정의 (서지안)

관리자 콘솔 📈 실적 분석 탭과 `/api/admin/analytics/*`가 계산하는 모든 숫자의 정의다.
코드(`server/analytics.js`)의 주석은 이 문서와 같은 말을 쓴다. 정의가 여기 없는 지표는 화면에 내지 않는다.
근거: 기획서 6.3(설비 상태창 목표 대비 진행률)·11장(기대효과 — 대응 시간 단축, 현장 가시성), 설계 원칙 5.3(수동/자동 상태 변경 동일 이벤트 규격).

## 0. 공통 — 기간·시각·데이터 원천

| 항목 | 정의 |
|---|---|
| 기간 | `from`·`to`는 `YYYY-MM-DD`(로컬 날짜, 양끝 포함). 기본값은 오늘 포함 최근 7일. `to`가 오늘이면 **지금 시각**까지만 계산한다(미래는 0). |
| 시각 | DB의 `changed_at`·`created_at`·`completed_at`은 모두 서버 로컬 시각 문자열 `YYYY-MM-DD HH:MM:SS`. 기존 `alarm-report`와 같은 방식으로 문자열 비교(`from 00:00:00` ~ `to 23:59:59`)한다. |
| 상태 이력 | `equipment_status_log` — 수동(작업자·관리자)과 자동(게이트웨이 계정 `users.emp_no='gateway'`) 변경이 **같은 표**에 같은 규격으로 쌓인다(5.3). 같은 상태로 다시 바꾸는 요청은 로그가 남지 않는다(`applyStatusChange`). |
| 실적 | `production_records.qty_good / qty_defect` — 작업지시(퀘스트) 완료 시 작업자가 **수동 입력**. `created_at`이 실적 시각. |
| 목표 | `work_orders.target_qty` — 작업지시 생성 시 관리자가 입력. |
| 설비 유형 | `equipments.type`(인터페이스 §1). 응답에 그대로 싣고 화면 라벨만 붙인다. |

## 1. 상태 점유 시간 (RUN / IDLE / STOP / ALARM 분)

기존 `todayStatusBreakdown`(대시보드 오늘 점유 시간)과 **같은 방식**을 기간으로 확장한 것이다.

1. 설비별 상태 로그를 `id` 순으로 늘어놓고, 각 로그의 상태는 **다음 로그 시각까지**(마지막 로그는 지금 시각까지) 유지된다고 본다.
2. 기간 시작 이전의 마지막 로그가 있으면 그 상태가 기간 시작 시점의 상태다(구간을 기간에 맞춰 자른다).
3. 로그가 **한 건도 없는** 설비는 `equipments.status`가 `status_since`부터 지금까지 유지된 것으로 본다(대시보드와 동일한 폴백 — 시드 데이터로 상태만 정해진 설비).
4. 로그가 있는 설비의 **첫 로그 이전** 시간은 상태를 알 수 없으므로 어느 상태에도 넣지 않는다 → `unknownMin`으로 따로 보고한다(시드 상태는 로그가 없어서 추정하지 않는다).
5. 구간을 `[기간 시작, min(기간 끝, 지금)]`으로 잘라 상태별로 합산한다(ms → 분, 소수 1자리).

`coveredMin = RUN+IDLE+STOP+ALARM`, `unknownMin = (기간 길이) − coveredMin`. `unknownMin`이 크면 화면에 "상태 미확인 N분"으로 표시한다.

## 2. 계획 시간 (plannedMin)

- 하루 계획 분 = `settings.policy.shiftMinutesPerDay` (1~1440). **설정이 없으면 1440(24h)**. 설정 위치: 관리자 콘솔 → 사용자 관리 → 운영 정책 → "1일 계획 가동 시간(분)".
- 기간의 날짜별로: 지난 날 = 하루 계획 분, **오늘 = min(하루 계획 분, 0시부터 지금까지 경과 분)**, 미래 날짜 = 0.
- 근무 시작 시각은 설정이 없으므로 모른다. 따라서 `shiftMinutesPerDay < 1440`이면 "하루 중 어느 시간대가 근무인지"는 구분하지 않고 **총량만** 계획 시간으로 쓴다. 근무 외 시간의 RUN도 RUN 시간에 들어가므로 가동률이 100%를 넘을 수 있고, 그 경우 100%로 상한하고 비고에 적는다.
- 모든 설비에 같은 계획 시간을 적용한다(설비별 근무 캘린더 없음).

## 3. OEE 3요소

| 지표 | 분자 | 분모 | null 조건 |
|---|---|---|---|
| **가동률 availability** | RUN 분(§1) | 계획 분(§2) | 계획 분 = 0 (미래 기간) |
| **성능 performance** | 양품 + 불량 (기간 내 `production_records` 합) | 목표수량(기간 내 작업지시 `target_qty` 합, §3.1) | 목표 = 0 |
| **품질 quality** | 양품 | 양품 + 불량 | 양품+불량 = 0 |
| **OEE** | availability × performance × quality | — | 셋 중 하나라도 null |

값은 0~1 비율(화면에서 %로 표시). 가동률은 `min(1, RUN/계획)`, 성능도 `min(1, 실적/목표)`로 상한한다 — OEE가 100%를 넘지 않게 하기 위해서다. 목표 초과 생산은 비고("목표 초과 생산 n/m")와 생산 표의 **달성률**(상한 없음, summary의 `attainment`)로 그대로 보여 준다.

### 3.1 기간 내 목표수량에 넣는 작업지시

설비 상태창 게이지(`queries.eqTargetQty`, "오늘 목표")와 **같은 규칙**을 기간으로 확장했다:

- `status = 'DONE'` 이고 `completed_at`이 기간 안 → 포함
- `status IN ('OPEN','IN_PROGRESS')` 이고 `created_at`이 기간 안 → 포함
- `CANCELED`는 제외

실적(`production_records`)은 `created_at` 기준이므로, 완료 시각과 실적 시각이 같은 정상 흐름에서는 분자·분모가 같은 기간에 잡힌다. 작업지시 없이 넣은 실적(`work_order_id NULL`)은 분자에만 들어간다.

### 3.2 요약(summary)

설비별 값의 평균이 아니라 **합계로 다시 계산**한다(가중 합산): `Σ RUN / Σ 계획`, `Σ(양품+불량) / Σ 목표`, `Σ 양품 / Σ(양품+불량)`. 따라서 실적이 없는 설비가 많아도 실적이 있는 설비의 품질이 평균에 희석되지 않는다. `equipmentsWithOee`는 OEE가 null이 아닌 설비 수.

## 4. 일별 생산 추이 (`/production`)

- `days[]`: 기간의 **모든 날짜**(데이터가 없는 날은 0). `good`·`defect`는 그날 `production_records` 합, `target`·`orders`는 §3.1 규칙으로 그날에 귀속된 작업지시의 목표 합·건수. `records`는 실적 입력 건수.
- `byEquipment[]`: 설비별 같은 합계(모든 설비를 넣고 0도 보여 준다 — 어떤 설비에 실적이 안 들어오는지 보는 용도).

## 5. 게이트웨이 연결 품질 (`/gateway`)

게이트웨이는 **상태가 바뀔 때만** 로그를 남긴다(같은 상태 재수집은 무시). 따라서 "샘플"은 원시 폴링 횟수가 아니라 **게이트웨이가 기록한 상태 변경 수**다. 원시 폴링 수는 DB에 없다(한계 §6).

| 필드 | 정의 |
|---|---|
| `protocol` | `equipments.data_source.protocol` (없으면 null) |
| `mode` | 기간 내 마지막 게이트웨이 로그의 `reason`에 `SIM`이 있으면 `sim`, 없으면 `live`; 게이트웨이 로그가 없으면 `none`. (게이트웨이가 켜져 있는지는 `/api/admin/gateway`가 실시간으로 답하므로 여기서는 이력 기준) |
| `samples` | 기간 내 `changed_by = gateway` 로그 수 |
| `statusChanges` | 기간 내 전체 상태 변경 수(수동 + 자동). `manualChanges = statusChanges − samples` |
| `alarmCount` | 기간 내 게이트웨이가 기록한 `ALARM` 진입 수 |
| `lastSeen` | 그 설비의 **가장 최근** 게이트웨이 로그 시각(기간과 무관 — "언제 마지막으로 살아 있었나") |
| `firstInRange` / `lastInRange` | 기간 내 첫·마지막 게이트웨이 로그 시각 |
| `medianGapSec` | 기간 내 연속 게이트웨이 로그 사이 간격의 중앙값(초). 상태가 얼마나 자주 바뀌는지의 척도 |
| `maxGapSec` | 기간 내 최대 간격(초). 설정된 `intervalMs`보다 훨씬 크면 그 사이 연결이 끊겼거나 상태가 안정적이었던 것 — **둘을 구분할 수 없다**(한계 §6) |
| `intervalMs` | `data_source.intervalMs` (설정값, 기본 1000) |

대상 설비: `data_source`에 프로토콜이 있는 설비 ∪ 기간 내 게이트웨이 로그가 있는 설비.

## 6. 데이터 한계 (화면에도 같은 말을 쓴다)

1. **실적은 수동 입력**이다. 작업자가 퀘스트를 완료하며 넣은 수량이라 입력 누락·지연이 그대로 성능·품질에 반영된다. 게이트웨이는 아직 상태만 수집하고 수량(카운터)은 수집하지 않는다.
2. **상태 이력은 변경 시점만** 남는다. 폴링이 끊겨도 로그가 없으므로 "상태가 유지됐다"와 "연결이 끊겼다"를 이력만으로 구분할 수 없다. `maxGapSec`은 힌트일 뿐이다.
3. **첫 로그 이전 상태는 모른다**(§1-4). 시드로 상태만 정한 설비는 `status_since`부터 그 상태로 본다.
4. **계획 시간은 총량**이다(§2). 교대 시작 시각·휴무일 캘린더가 없어 야간·주말도 계획에 들어간다(24h 기본). `shiftMinutesPerDay` 설정이 들어오면 총량만 줄어든다.
5. **목표수량 귀속**은 완료일(DONE) 또는 생성일(OPEN/IN_PROGRESS) 기준이라, 기간을 걸쳐 진행되는 작업지시는 한쪽 기간에만 잡힌다.
6. **SIM 모드 로그**는 가짜 데이터다. `reason`에 `SIM`이 붙어 있으며 화면에 `sim`으로 표시한다. SIM 표기가 생기기 전(초기 데모)의 로그는 `live`로 보이지만 실제 장비가 아니었을 수 있다.
7. 현재 DB(2026-09-07 기준): 상태 로그 196건 전부 2026-08-13 13:48~15:44, 작업지시 2건, 실적 1건. 기본 기간(최근 7일)은 비어 있으므로 "데이터 없음"이 정상이다. 2026-08-13을 포함한 기간으로 조회해야 값이 보인다.

## 7. 최민준에게 요청한 설정·훅 (handoff-서지안.md 참조)

- 운영 정책에 `shiftMinutesPerDay`(1~1440) 항목 추가 — 스프린트 1 라운드 3에서 반영됨(§2).
- 향후: 게이트웨이 폴링 카운트(수신/실패)를 별도 표에 남기면 §5의 한계 2를 해소할 수 있다(스키마 제안, 라운드 3 이후).
- 숨김 설비(`equipments.hidden = 1`, 인터페이스 §7): 분석 API는 `listEquipments` 결과에 `hidden` 필드가 있으면 참인 행을 제외한다(컬럼이 없으면 전부 포함). `listEquipments` 자체가 숨김을 거르면 중복 필터라 무해하다.

## 8. 라인 밸런스 (`/line-balance`, 스프린트 2)

BOP(공정) 데이터로 계산하는 **설계 능력(capacity) 지표**다. 상태 이력·실적·기간 필터와 무관하며, 숫자가 바뀌는 조건은 공정 C/T·병렬 대수·가동시간·OEE 가정값뿐이다.
원천: `processes` 테이블(인터페이스 §7 — `POST /api/admin/bop/import`가 `docs/bldc/bldc-500w-48v.json`을 적재) + `equipments.op`(설비 ↔ 공정 연결).
기준값: xlsx `12_Line_Balance` 시트 — 가동 **20 h/일**, OEE **0.85**, 목표 UPH **60**, 병목 "OP-A40 45초(병렬 2대 후)" · "OP-B110 60초".

### 8.1 입력 (쿼리 파라미터 · 공정 필드)

| 항목 | 정의 |
|---|---|
| `product` | 제품 코드(`products.code`). 없으면 `products`의 첫 행. |
| 공정 C/T `ctSec` | `processes.ct_sec`(초). BOP 시트의 C/T. 표준·병목·QC·완성 공정은 **1개당** 시간, 배치 공정은 **1배치당** 시간이다. |
| 공정유형 `kind` | `processes.kind` — 표준 / 병목 / QC / 배치 / 완성 (시트 표기 그대로). **"병목" 표기는 시트 작성자의 라벨일 뿐**이며 병목 판정은 C/T로 다시 한다(둘이 다르면 비고에 적는다). QC·완성 공정은 흐름상 표준 공정과 같게 취급한다(검사도 1개당 시간을 쓴다). |
| 배치 크기 `batchSize` | `note`의 `N ea/배치`(예: `30ea/배치`)에서 읽는다. 없으면 null → 개당 C/T를 낼 수 없어 비고 "배치 크기 미상". |
| 병렬 대수 `parallel` | 쿼리 `parallel[OP-A40]=2` 또는 `parallel=OP-A40:2,OP-B110:1`. 기본 **1**. 1~20 정수. |
| 병렬 권장 `parallelHint` | `note`의 `병렬 N대 권장`에서 읽어 응답에 싣는다. 쿼리 `hints=1`이면 `parallel`이 지정되지 않은 공정에 이 값을 적용한다(기본 0 = 적용 안 함 → 화면은 `hints=1`을 기본으로 보내고 토글로 끈다). |
| 가동시간 `hours` | 시간/일. 기본 **20**(xlsx). 0.1~24. |
| OEE `oee` | 기본 **0.85**(xlsx). 0.01~1. **§3의 실측 OEE가 아니라 계획 가정값**이다. 실측값을 넣어 보려면 §3의 값을 직접 입력한다. |
| 목표 UPH `targetUph` | 시간당 목표 대수. 기본 **60**(xlsx). 1~100000. |

`dailySec = hours × 3600 × oee` (기본 61,200초 — xlsx "일 가동초").

### 8.2 공정 단위

- **유효 C/T** `effectiveCtSec = ctSec ÷ parallel` — 표준·병목·QC·완성 공정. 같은 공정을 n대가 나눠 하면 라인 관점의 1개당 시간은 1/n이다.
- **배치 공정 개당 C/T** `perUnitCtSec = ctSec ÷ batchSize ÷ parallel` — 배치 공정(kind = 배치)만. 화면에 "3600초/30ea = 120초/ea"처럼 **병기**한다.
- 배치 공정은 **라인 C/T 합계와 병목 판정에서 제외**한다(xlsx와 같은 취급 — 배치 설비는 버퍼를 두고 흐름과 분리해 돌린다는 가정). 단, `perUnitCtSec > 병목 C/T`이면 경고 **"배치 공정이 실질 병목"**을 낸다: 그 배치 설비를 `ceil(perUnitCtSec ÷ 병목 C/T)`대 두거나 배치 크기를 키워야 흐름을 따라간다. (BLDC 기준값에서 OP-A90 건조로는 120초/ea > 45초 → 경고. xlsx는 이를 무시하므로 숫자는 xlsx와 같고 경고만 추가된다.)
- `isBottleneck`: 라인의 병목 공정이면 true.
- 설비 연결 `equipment`: `equipments.op = processes.op`인 설비(`hidden` 제외) 중 첫 번째 `{ id, code, name, type, status }`, 없으면 null. `linkedCount`는 그 op에 연결된 설비 수(병렬 설비를 따로 등록한 경우 2 이상). **연결 설비 수는 `parallel`을 자동으로 바꾸지 않는다**(설정값과 실제 대수가 다르면 비고에 적는다).

### 8.3 라인 단위 (`processes.line`별)

| 지표 | 정의 |
|---|---|
| 병목 공정 `bottleneck` | 유효 C/T가 **최대**인 비배치 공정. 동률이면 시트의 `kind = 병목` 표기가 있는 것, 그것도 없으면 `seq`가 앞선 것. 동률인 나머지 공정은 `tiedWith[]`에 싣고 비고에 "병목과 동률"로 적는다(어느 쪽을 골라도 C/T·UPH는 같다). 병목 C/T = 그 유효 C/T. (BLDC 조립 라인은 OP-B90 60초와 OP-B110 60초가 동률 → 시트 표기대로 B110.) |
| 라인 C/T 합계 `sumCtSec` | Σ `ctSec`(비배치, 병렬 반영 안 함 — 1대를 만드는 작업 내용 총량) |
| 유효 C/T 합계 `sumEffectiveCtSec` | Σ `effectiveCtSec`(비배치) |
| 밸런스 효율 `balanceEff` | `sumEffectiveCtSec ÷ (비배치 공정 수 × 병목 C/T)` — 라인 밸런싱 효율의 표준 정의(각 공정이 병목 속도로 돌 때 실제 작업하는 시간 비율). 1에 가까울수록 고르다. |
| UPH `uph` | `3600 ÷ 병목 C/T` (소수 1자리) |
| 일 생산량 `dailyOutput` | `dailySec ÷ 병목 C/T` = `hours × 3600 × oee ÷ 병목 C/T` (정수 내림) |
| 목표 달성률 `attainment` | `uph ÷ targetUph` (상한 없음) |
| 목표 C/T `taktSec` | `3600 ÷ targetUph` — 목표를 맞추려면 모든 비배치 공정의 유효 C/T가 이 값 이하여야 한다. 넘는 공정은 `overTakt`에 나열. |
| 설비 연결 | `linkedCount` / `processCount`, 미연결 공정 `unlinked[]` |

### 8.4 제품 단위 (`summary`)

- 라인은 직렬이다(아마추어 라인 → OP-B50에 SA-1000 공급 → 조립 라인). 따라서 **제품 UPH = min(라인 UPH)**, **제품 일 생산량 = min(라인 일 생산량)**, 제품 달성률 = 제품 UPH ÷ 목표 UPH. 가장 느린 라인을 `slowestLine`으로 표시한다.
- 라인 사이 버퍼·재공(WIP)·수율은 고려하지 않는다(§8.6).

### 8.5 기준값 대조 (xlsx 12_Line_Balance, 기본값 hours 20 · oee 0.85 · targetUph 60)

| 라인 | 병목 | 병목 C/T | UPH | 일 생산량 | 달성률 |
|---|---|---|---|---|---|
| 아마추어 라인 (`parallel[OP-A40]=2` 또는 `hints=1`) | OP-A40 Needle Winding | 90 ÷ 2 = **45** | **80** | 61200 ÷ 45 = **1360** | 133% |
| 아마추어 라인 (병렬 없음) | OP-A40 | 90 | 40 | 680 | 67% |
| 조립 라인 | OP-B110 성능/기능 시험 | **60** | **60** | **1020** | 100% |
| 제품 | 조립 라인이 결정 | 60 | 60 | 1020 | 100% |

라인 C/T 합계: 아마추어 240.5초(8공정, 배치 A80·A90 제외), 조립 465초(14공정). 밸런스 효율: 아마추어 195.5 ÷ (8×45) = 54.3%, 조립 465 ÷ (14×60) = 55.4%.

### 8.6 한계 (화면 비고에도 같은 말)

1. **C/T는 BOP 설계값(수기)** 이다. 실측 사이클 타임이 아니다. 게이트웨이가 사이클 카운트를 수집하기 전까지는 §3의 실적과 연결되지 않는다.
2. **OEE 0.85는 가정값**이다. §3의 실측 OEE와 다르며, 실측을 넣어 보는 것은 사용자의 몫이다.
3. **배치 공정**은 병목 판정에서 빠진다(xlsx 기준). 개당 C/T가 병목보다 크면 경고만 낸다.
4. 라인 간 **버퍼·재공·수율·셋업 시간**을 고려하지 않는다. 일 생산량은 병목 속도 × 가동초 × OEE의 단순 계산이다.
5. `kind = 병목` 라벨과 계산 병목이 다를 수 있다. BLDC 기준값에서는 둘이 같다(A40은 병렬 2대 후 45초여도 다음 공정 A50 40초보다 크다).
6. 설비 연결은 `equipments.op` 1:1 기준이다. `processes` 테이블·`equipments.op` 컬럼이 아직 없으면 API는 빈 결과와 `reason`을 돌려주고, 화면은 "데이터 없음 · 이유"를 표시한다. BOP를 적용하지 않은 DB에서도 마찬가지다(관리자 콘솔 → 제품 라인 적용).
