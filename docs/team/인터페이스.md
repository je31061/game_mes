# 인터페이스 계약 (세 에이전트 공통)

변경 절차: 협업로그에 제안 → 소유자가 반영. 여기 적힌 것이 원천이다.

## 1. 설비 유형 (owner: 최민준, 유형 목록 제안권: 한도윤)

`equipments.type TEXT NOT NULL DEFAULT 'generic'`

| type | 설명 | 시드 매핑 (코드 접두) |
|---|---|---|
| `press` | 프레스 | PRS-* |
| `welder` | 용접기 | WLD-01, WLD-02 |
| `robot` | 용접/다관절 로봇 | WLD-03 |
| `assembly` | 조립 라인(컨베이어) | ASM-* |
| `inspector` | 검사기(비전) | INS-* |
| `packer` | 포장기 | PKG-* |
| `cnc` | CNC 가공기 | CNC-* |
| `generic` | 미지정(기존 절차적 큐브) | 그 외 |

- API: `PUT /api/admin/equipments/:id` 본문 `type`, `POST /api/admin/equipments` 본문 `type`, 배치 JSON `equipments[].type`(선택), `GET /api/admin/equipments`·`init`·`world:refresh`의 equipment 객체에 `type` 포함.
- 관리자 콘솔: 맵 에디터 설비 패널과 설비 마스터 표에 유형 선택.

## 2. 설비 스프라이트 (owner: 한도윤)

- 경로: `public/assets/equipment/<type>.png` (RGBA), 매니페스트 `public/assets/equipment/manifest.json`
- 캔버스: **192×192 px**. 아이소메트릭 2:1(디메트릭). 설비는 타일 1칸(바닥 마름모 **폭 64px · 높이 32px**)에 놓인다.
- 앵커: 마름모 중심이 이미지의 **(96, 150)**. 게임은 `setOrigin(0.5, 150/192)`로 놓는다. 설비 높이는 위로 자유(최대 y=10까지).
- 상태 램프: 게임이 그리는 램프(원) 위치를 매니페스트의 `lamp: {x, y}`(이미지 픽셀 좌표)로 지정. 램프 뒤에 실사 경광등 몸통을 모델에 포함하면 좋다.
- 라벨(설비명)은 게임이 이미지 위쪽에 그린다(`labelY` 픽셀, 기본 -0 = 이미지 상단).
- 매니페스트 형식:
  ```json
  { "version": 1, "tile": { "w": 64, "h": 32 }, "anchor": { "x": 96, "y": 150 },
    "types": { "press": { "file": "press.png", "lamp": { "x": 118, "y": 52 }, "labelY": 8 }, ... } }
  ```
- 파일이 없는 유형·`generic`은 게임이 기존 절차적 큐브를 그린다(하위 호환).
- 라이트 테마에서도 보이도록 스프라이트에 바닥 그림자(반투명)를 포함한다. 배경은 투명.
- 제작 파이프라인: `assets/blender/build_equipment.py`(bpy, 모델 생성+렌더), `assets/blender/render.cmd`(Blender 5.2 배치 실행), `assets/blender/postprocess.py`(PIL: 트리밍·앵커 정렬·매니페스트 갱신). Blender 경로는 `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe`. 카메라: 직교, 회전 **(60°, 0, 45°)**로 2:1 비율(마름모 종횡비 = 1/cos(rx); 63.435°는 2.236:1이라 사용하지 않음 — 협업로그 2026-09-07 한도윤). 중간 렌더는 `assets/blender/out/`(커밋 제외).
- 렌더 산출물은 커밋한다(다른 PC에 Blender가 없어도 게임이 동작해야 함). `.blend`는 커밋하지 않는다(스크립트로 재생성).

## 3. 게임 스프라이트 로더 (owner: 최민준)

- 부팅 시 `manifest.json`을 읽어 존재하는 유형의 텍스처를 preload. 매니페스트가 없으면 전부 절차적 큐브.
- `addEquipment(eq)`: `eq.type`이 매니페스트에 있으면 이미지 스프라이트 + 램프(매니페스트 좌표) + 라벨, 없으면 기존 큐브. 클릭 영역은 이미지의 불투명 픽셀(pixelPerfect). 깊이 정렬은 기존 `isoY` 규칙 유지.
- 클릭 알파 임계값 **64** (`SPRITE_HIT_ALPHA`, 2026-09-08 결정): 알파 64 미만 픽셀은 클릭이 통과한다. 따라서 바닥 그림자는 알파 **63 이하**, 본체·윤곽은 **64 이상**(권장 본체 255)으로 렌더한다. 현재 그림자 밴드 28~60은 그대로 통과 — 한도윤은 `SHADOW_A_MIN`을 바꿀 필요 없음.
- `reloadWorld`에서 유형이 바뀐 설비는 재생성.

## 4. 분석 API (owner: 서지안) — 파일 `server/analytics.js`

`export function registerAnalytics(app, { requireAdmin, db, queries, settings })` 를 최민준이 `server/index.js`에서 호출한다. 서지안은 이 함수 안에서 라우트를 등록한다. 모든 라우트는 `requireAdmin`.

| 라우트 | 응답 |
|---|---|
| `GET /api/admin/analytics/oee?from=YYYY-MM-DD&to=YYYY-MM-DD&equipmentId=` | `{ range, equipments: [{ id, code, name, type, availability, performance, quality, oee, runMin, plannedMin, good, defect, target }], summary }` |
| `GET /api/admin/analytics/production?from&to&equipmentId=` | `{ days: [{ date, good, defect, target, orders }], byEquipment: [...] }` |
| `GET /api/admin/analytics/gateway?from&to` | `{ equipments: [{ id, code, protocol, mode, samples, statusChanges, alarmCount, lastSeen }] }` |

정의(서지안이 문서화·구현, 근거는 기획서 6.3·11장):
- 가동률(availability) = RUN 시간 / 계획 시간(기본: 기간 내 24h 또는 설정된 근무시간, `settings.policy.shiftMinutesPerDay` 있으면 그 값)
- 성능(performance) = 실제 양품+불량 / 목표수량 (목표 0이면 null)
- 품질(quality) = 양품 / (양품+불량)
- OEE = 세 값의 곱 (null이 있으면 null, 이유 표시)

## 5. 분석 화면 (owner: 서지안) — 파일 `public/js/analytics.js`, `public/css/analytics.css`

- 최민준이 `admin.html`에 탭 버튼 `data-tab="analytics"`, 컨테이너 `<div class="tabview" id="tab-analytics"></div>`, `<script src="js/analytics.js">`, css link를 넣는다.
- 서지안의 스크립트는 `window.FWAnalytics = { mount(container, api) }` 를 정의하고, 최민준의 admin.js가 탭 활성화 시 `FWAnalytics.mount($('tab-analytics'), api)` 를 호출한다. `api(path, opts)`는 admin.js의 인증 fetch 래퍼(JSON 반환).
- 차트는 외부 라이브러리 없이 인라인 SVG/canvas. 테마 변수(`--text`, `--muted`, `--run` 등) 사용.

## 7. 제품 공정(BOP)·단품(BOM) 데이터 모델 (owner: 최민준, 스프린트 2)

원천: `docs/bldc/bldc-500w-48v.json` (`scripts/bldc/extract.py`가 xlsx/PDF에서 생성). 서버는 이 JSON을 `POST /api/admin/bop/import`로 받아 아래 테이블에 upsert 한다.

```sql
products         (code TEXT PK, name TEXT, spec_json TEXT)
processes        (id PK, product_code, op TEXT, seq INT, line TEXT, name TEXT, equipment_hint TEXT,
                  input_text TEXT, output TEXT, ct_sec REAL, kind TEXT, qc TEXT, note TEXT, stage_pn TEXT,
                  UNIQUE(product_code, op))
parts            (pn TEXT PK, name TEXT, spec TEXT, level TEXT, parent_pn TEXT, parent_name TEXT,
                  qty_per_parent REAL, qty_per_product REAL, unit TEXT, image TEXT)   -- image: public/assets/parts/<file> 있을 때
process_inputs   (process_id INT, pn TEXT, qty REAL, PRIMARY KEY(process_id, pn))
equipments.op    TEXT NULL   -- 설비 ↔ 공정 연결 (예: 'OP-A40'). 배치 JSON equipments[].op, 설비 API/콘솔 유형 옆 select
equipments.hidden, zones.hidden  INTEGER DEFAULT 0  -- 라인 전환 시 이력 있는 설비를 지우지 않고 맵·분석에서 숨김
```

- 서브어셈블리 9종(SA-1000 등)도 `parts`에 `level='L1'`로 넣고, 분해도 이미지가 있으면 `image`에 파일명.
- `POST /api/admin/layout`에 `"replace": true` 옵션: 파일에 없는 설비·존은 `hidden=1`(삭제 아님). `hidden` 설비는 `init`·`world:refresh`·분석·게이트웨이 대상에서 제외, 콘솔 설비 마스터에는 "숨김" 표시와 복원 버튼.
- `equipment:detail` 응답에 추가:
  ```
  process: { op, seq, line, name, equipmentHint, ctSec, kind, qc, note, output, inputText,
             inputs: [{ pn, name, spec, qty, unit, parentPn, parentName, image }],
             stage: { pn, file, label, group } | null }      // stage_pn 기준 분해도 단계, null이면 완성품
  ```
- `GET /api/bop/exploded` (로그인 사용자): `{ product, stages: [{ stage, pn, file, label, group, processes: [op...] }], final: [op...] }` — 분해도 모달용. `final`은 `stage_pn`이 null인 완성품 공정.
- `GET /api/admin/bop` : 공정 24건 + 투입 단품 수, 설비 연결 현황(어느 공정에 설비가 없는지).
- 구현 메모 (2026-09-09 라운드 1, 최민준):
  - `products.spec_json` = `{ spec, exploded[], lineBalance, source, importedAt }` — JSON의 비표 블록 원문. 분해도 단계 순서·라벨·그룹은 여기서 읽는다(별도 표 없음). 라인 밸런스 기준값(xlsx 12_Line_Balance)도 여기 있다.
  - `process_inputs.qty` = 제품 1대당 수량(`parts.qty_per_product`, 서브어셈블리는 `qty`). 상태창 표의 "수량/단위"가 이 값.
  - 같은 P/N이 서브어셈블리와 단품 양쪽에 있으면(FS-7010·FS-7020) `level='L1'`·이미지 우선, 단품의 규격은 보존(가져오기 결과 `warnings`에 표시).
  - `parts.image` = `<pn>.png` 있으면 그것, 없으면 `<parentPn>.png`(복합 부모 `HA-3000/EX-5000`은 없음). 상태창은 둘 다 없으면 공정의 `stage.file`로 대체.
  - 설비 `op` → 공정은 `processes WHERE op = ? ORDER BY product_code LIMIT 1`(제품 1개 전제). 제품이 늘면 `equipments.product_code`를 추가한다.
  - `POST /api/admin/bop/apply-sample` (requireAdmin): `docs/bldc/bldc-500w-48v.json` → `layout-bldc-500w.json` 순서로 서버가 읽어 적용. 응답 `{ ok, bop: {processes, parts, inputs, ...}, layout: {zones, equipments, links, warnings} }`.
  - `GET /api/admin/equipments` 응답에 `hiddenZones`, `processes: [{ productCode, op, seq, line, name }]` 추가(콘솔 공정 select·존 복원용). `equipments`는 숨긴 것 포함(`hidden` 플래그). `PUT /api/admin/equipments/:id` 본문 `op`(null=해제)·`hidden`(복원 시 속한 존도 복원), `PUT /api/admin/zones/:id` 본문 `hidden`.
  - 숨김 제외는 `queries.listEquipments`·`listZones`·`listLinks`(양끝 hidden=0)·`alarmEquipments`에 `WHERE hidden = 0`이 들어가 있어 이 쿼리를 쓰는 곳(분석·게이트웨이 포함)은 자동 제외. 전체 조회는 `listAllEquipments`·`listAllZones`.

## 8. 설비 상태창 "공정 · 단품" (owner: 최민준)

- 상태창(HUD)에 "공정 · 단품" 섹션: 공정번호·공정명·라인·C/T·공정유형·품질관리항목, **투입 단품 표**(썸네일 = 서브어셈블리 이미지, P/N, 품명, 규격, 수량/단위), 산출물. 공정이 연결되지 않은 설비는 섹션을 감춘다.
- 버튼 **🔩 분해도**: 모달에 분해도 9단계를 조립 순서대로 가로 스크롤(이미지 + P/N + 라벨 + 그룹), 현재 설비의 단계를 강조. 완성품 공정(시험·포장)은 전체를 같은 강조.
- 이미지는 `public/assets/parts/<pn>.png`(PDF 추출, 325×484, 흰 카드 배경). 라이트·다크 테마 모두에서 카드 그대로 보이면 됨.
- 썸네일 경로(2026-09-10 라운드 2 확정): **투입 단품 표 = `/assets/parts/thumb/<pn>.png`**(한도윤, 96×96 불투명 흰 배경·1px 회색 테두리, 표시 36×36) — 로드 실패 시 원본 `/assets/parts/<pn>.png`로 폴백, 그것도 없으면 빈 칸. **분해도 모달 = 원본**(325×484). 파일명은 두 폴더가 같으므로(`parts.image`) 서버 변경 없음. 재생성 `python assets/blender/make_part_thumbs.py`.
- 구현(라운드 1): `index.html` `#eq-proc-section`(공정 정보 grid·단품 표·산출물·`#eq-exploded` 버튼), `#exploded-panel`(가로 스크롤 strip, 현재 단계 `.ex-card.cur`, 완성품 카드 `.final`). 스타일은 `public/css/style.css` "공정 · 단품"·"분해도 모달" 절. `app.js` `renderProcess(res.process)`·`openExploded()`(`/api/bop/exploded` 1회 캐시, `world:refresh`에 무효화).

## 10. 자재(Material) API · 자재 탭 (스프린트 3 — owner: 최민준 API, 서지안 화면, 노하린 인수 테스트)

원천 계약: `docs/4m/ddl-v1.sql`(스키마·트리거·호환 뷰, 윤태경), `docs/4m/cleansing-v1.json`(적재 규칙), 계획서 v1.0 §5.9 기준 쿼리.
모든 라우트는 `requireAdmin`, 오류는 `{ error }`. 트리거가 거부한 쓰기는 **400**이고 `error`에 트리거 문자열(`R-1: ...`)을 그대로 담는다.
(표는 2026-09-13 라운드 5 에 **구현(`server/materials.js`) 기준으로 정정** — 서지안 21:30·노하린 20:10/21:30 요청. 이 표가 곧 실제 응답이다.)

| 라우트 | 응답 |
|---|---|
| `GET /api/admin/materials/summary` | `{ items, classes, bomHeaders, bomLines, lots, processMaterial:{in,out}, itemsByKind, phantoms, tmpItems, check: {<규칙코드>: 건수}, schema:{compatViews,legacyTables} }` — `check` 는 `v_chk_summary` 그대로 |
| `GET /api/admin/materials/check` | `{ summary, details: { <규칙코드>: [detail…] } }` — `v_chk_*` 전부(순환 경로는 `R-1` 의 detail) |
| `GET /api/admin/materials/uom` | `[{ code, name, kind, decimals }]` |

## 11. 품목 등록 화면 (스프린트 4 — owner: 최민준 API·화면)

§10 자재 탭은 **있는 기준을 보는** 화면이다. 이 화면은 반대로 **품번 하나를 새로 만들고 BOM 에 붙이는** 일만 한다. 현장 담당자가 쓰는 화면이라 필수는 세 칸(품번·품명·품목구분)이고, 나머지는 품목구분을 고르면 서버가 준 기본값이 따라온다.

### 11.1 품목구분 — 표시축 (`item.item_group`)

ERP/MES 품목 마스터의 공통 관행(SAP 자재유형 FERT·HAWA·HALB·ROH·VERP·HIBE / 국내 ERP 품목구분 제품·상품·반제품·원재료·부재료·저장품)을 현장 용어 9개로 줄였다. **전개·소요량·점검은 전부 `item_type` 으로 계산한다** — `item_group` 은 화면 표시와 기본값 결정에만 쓴다.

| 코드 | 표시 | `item_type` | `source_type` | 추적 기본 | 비고 |
|---|---|---|---|---|---|
| `PROD` | 제품 | FG | MAKE | SERIAL | 만들어 파는 완성품 |
| `GOODS` | 상품 | FG | BUY | LOT | 사서 그대로 파는 것 |
| `SEMI` | 반제품 | SA | MAKE | LOT | 자기 BOM 을 가진다 |
| `WIP` | 재공품 | SA | MAKE | LOT | 표준 ERP 는 품목이 아니라 재고 상태로 본다 — 품번을 따로 딸 때만 |
| `PART` | 부품 | PT | BUY | NONE | 사 오는 단품 |
| `RAW` | 원자재 | RM | BUY | LOT | 원재료도 이 칸 |
| `SUB` | 부자재 | CN | BUY | NONE | 제품에 남지만 주자재가 아닌 것 |
| `CONS` | 소모품 | CN | BUY | LOT | 사용기한 기본 365일 |
| `PACK` | 포장재 | PK | BUY | NONE | |

`item_group` 이 비어 있는 행(적재기 산출·옛 데이터)은 읽을 때 `item_type`+`source_type` 에서 유도해 보여준다(`groupDerived: true`). `server/db.js` 가 부팅 시 빈 행을 1회 채운다.

### 11.2 `item` 새 컬럼 3종 (전부 NULL 허용 — 적재기·점검 뷰·`expected` 대조에 영향 없음)

| 컬럼 | 뜻 |
|---|---|
| `item_group` | 위 표의 코드 |
| `use_to` | **사용기간 종료일**(YYYY-MM-DD). NULL = 무기한. **시작일은 `eff_from`** 을 그대로 쓴다 |
| `shelf_life_days` | 사용기간의 길이(일) = `use_to` − `eff_from`. 화면은 날짜 두 개로 받고 이 값은 그때 계산해 넣는다. 로트 유효일 = 입고일 + 이 값. NULL = 무기한 또는 분류(`mat_class.shelf_life_days`) 기본값 상속 |
| `in_uom` · `in_qty` | **기본** 입고단위와 환산. 1 `in_uom` = `in_qty` × `base_uom` (예: 1 BOX = 100 EA). 거래처별로 포장이 다르면 `item_partner.order_uom` 이 이긴다(§11.5.4). **재고·BOM·로트는 언제나 `base_uom` 으로만 돈다** — 이건 발주·입고 표기용이고 `uom_conv` 와 무관하다 |

`ddl-v1.sql` 의 `CREATE TABLE item` 에 들어 있고(새 DB), 기존 DB 는 `server/db.js` 가 `PRAGMA table_info` 로 확인해 `ALTER TABLE` 한다. DDL 문 개수는 85 그대로다.

| `GET .../items?group=` | §10 목록에 품목구분 필터 추가(`item_group` 이 빈 행도 유도값으로 걸린다). 목록 응답에만 시트용 요약 2개가 더 붙는다 — `usedIn`(지금 유효한 `bom_line` 중 이 품목이 자식인 건수) · `hasBom`(자기 BOM 헤더 보유) |
| `POST/PUT .../items` | §10 본문에 `group`(=`itemGroup`) · **`useFrom`·`useTo`**(사용기간, YYYY-MM-DD) · `inUom` · `inQty` 추가. `useTo` 를 주면 `shelf_life_days` 를 두 날짜 차이로 계산해 넣고, 역순·형식 오류는 400. 옛 경로 `shelfLifeDays`(일수)도 그대로 받는다 — 날짜를 안 줬을 때만 쓰이고 `use_to` 를 `시작일+일수` 로 채운다. `group` 을 주고 `classId` 를 안 주면 그 구분의 `defaultClassId` 로 넣는다 → **품번·품명·구분 3칸만으로 등록된다**. `kind`·`sourceType` 을 직접 주면 그쪽이 이긴다 |
| `POST .../bom-attach` | `{ parentPn, childPn, qtyPer, uom?, op?, bopLink?, note? }` → `{ ok, header, line, createdHeader, linkedOp }`. 상위 품목의 현재 헤더(ACTIVE>APPROVED>DRAFT)에 라인 1행을 덧붙이고, 헤더가 없으면 ACTIVE 로 만든다. **운영 BOM 에도 붙는다** — 라인 `valid_from` 이 오늘이라 과거 전개 결과는 그대로다(§7.3 "덮어쓰지 않는다"). `op` 를 주면 `process_material` IN 1행까지 만들어 BOP 에 연결한다(`issue_method` 는 품목 분류 기본값). 같은 자식이 이미 유효하면 400. 트리거 위반(R-1 순환·R-22 공정 순서)은 그대로 400 으로 올라온다 |
| `DELETE/PUT .../bom-lines/:id` | 화면의 "빼기" — DRAFT 헤더면 DELETE, 운영·승인 헤더면 `effTo` 를 어제로 끊는다(R-11) |

`itemJson` 추가 필드: `group, groupName, groupDerived, useFrom(=eff_from), useTo, useToEffective, useToSource(item|class|null), shelfLifeDays, shelfLifeSource, shelfLifeEffective, inUom, inQty`. `useToEffective` 는 저장된 종료일이 없을 때 `시작일 + 분류 기본 일수` 로 **계산해 보여 주는** 날짜다(저장하지 않는다 — 화면은 `*` 로 표시). 기존 필드는 그대로라 §10 계약과 자재 탭은 무수정.

### 11.4 화면 규칙

- 파일: `public/js/items.js`(`window.FWItems = { mount(container, api) }`) · `public/css/items.css`(`.fwi-*`). `admin.html` 탭 `data-tab="items"`(라벨 "📦 품목 등록")·`#tab-items`, `admin.js` 의 `mountItems()`.
- 화면 구조는 **위쪽 품목 시트 + 아래쪽 등록 폼**이다. 시트는 엑셀처럼 보고 쓰라고 만든 것 — 머리글 고정(`position: sticky`)·첫 열(#) 고정·격자선·얼룩 줄·머리글 클릭 정렬(같은 열 다시 누르면 역순)·단종/중지 행 취소선·팬텀 배지·`⬇ 엑셀(CSV)`(UTF-8 BOM 을 붙여 엑셀에서 한글이 깨지지 않는다). 열 정의는 `items.js` 의 **`COLS` 배열 하나**가 화면·정렬·CSV 를 동시에 정한다 — 열을 늘리려면 거기만 고친다.
- 시트 열 14개: 품번 · 품명 · 품목구분 · 분류 · 규격·재질 · 기준단위 · 입고단위(`BOX = 100 EA` 로 합쳐 보여 준다) · **사용 시작일 · 사용 종료일**(`*` 는 분류 기본 일수로 계산한 값, 없으면 `무기한`) · 추적 · 조달 · 쓰이는 곳 · 자체 BOM · 상태.
- **폭에 따라 열이 줄어든다.** `COLS[].pri`(1~4) 와 CSS `@container fwi` 가 짝이다 — 1340px 이하 pri4(분류·규격·추적·자체 BOM), 1080px 이하 pri3(입고단위·사용 시작일·조달), 820px 이하 pri2(기준단위·사용 종료일·쓰이는 곳)가 숨고, pri1(품번·품명·품목구분·상태)은 어떤 폭에서도 남는다. 뷰포트가 아니라 **탭 컨테이너** 기준이라 사이드바를 접거나 창을 반으로 나눠도 맞다. `#`·품번 열은 가로 스크롤에도 붙어 있고(620px 이하에서는 고정을 푼다) 등록 폼은 `auto-fit minmax(230px)` 로 1~4단이 된다.
- 행을 누르면 아래 폼이 열리고(`#fwi-editor`), `닫기` 로 접는다. `+ 새 품목` 은 빈 폼을 열고 품번 칸에 포커스를 준다.
- **새 품목은 `DRAFT`(작성중)로 시작**한다. BOM 에 붙는 순간 `ACTIVE` 로 올린다 — 쓰이는 곳 없는 ACTIVE 품목은 점검 R-4 에 고아로 잡히기 때문이다. 단독으로 쓰는 품목이면 사용자가 직접 사용으로 바꾸고, 화면은 그때 R-4 경고를 띄운다.
- 품목구분을 바꾸면 분류·조달·추적·사용기한 기본값이 따라오되 **사용자가 직접 건드린 칸은 덮어쓰지 않는다**(`touched`).
- 트리거 위반 메시지는 현장 말로 바꾸고 원문을 괄호로 남긴다(`plain()`): R-22 → "그 공정은 상위 품목이 이미 완성된 뒤입니다 …".

## 12. 거래처 마스터 (스프린트 4 — owner: 최민준)

매입처와 매출처를 **한 표**에 두고 거래구분으로 나눈다. 사서 팔기도 하는 곳이 흔해 ERP 들이 공통으로 쓰는 방식이다.
표는 `server/db.js` 의 `partners` — 자재 기준 v1.0(`ddl-v1.sql`)은 건드리지 않는다(문 85개·인수 기준선 유지).

### 12.1 거래구분 · 상태

| 거래구분 | 뜻 |
|---|---|
| `BUY` 매입 | 우리가 사 오는 곳 — 자재·부품 공급사 |
| `SELL` 매출 | 우리가 파는 곳 — 고객사 |
| `BOTH` 매입·매출 | 사기도 하고 팔기도 하는 곳 — 사급·임가공이 얽힌 협력사 |
| `ETC` 기타 | 외주·운송·용역처럼 자재가 오가지 않는 곳 |

**`kind=BUY` 로 거르면 `BOTH` 도 함께 나온다**(`SELL` 도 마찬가지). 실제로 그 역할을 하는 곳이기 때문이고, `meta` 의 칩 건수도 같은 규칙으로 센다 — 목록과 건수가 어긋나지 않게.

상태는 `ACTIVE` 거래중 · `HOLD` 거래보류 · `CLOSED` 거래종료. **삭제는 405** — 지우면 과거 전표의 거래처가 사라진다(품목의 R-11 과 같은 규칙).

### 12.2 API

| 엔드포인트 | 계약 |
|---|---|
| `GET /api/admin/partners/meta` | `{ kinds:[{code,name,hint,count}], statuses:[{code,name,count}], total, nextCode }` — 화면은 이 응답만 보고 칩·드롭다운을 그린다. `nextCode` 는 비어 있는 첫 자동 코드 |
| `GET /api/admin/partners?q=&kind=&status=` | 목록. `q` 는 코드·상호·사업자번호·대표자·담당자를 함께 본다. 정렬은 거래중 → 보류 → 종료, 그 안에서 코드순. **연결 품목 건수**(`buyItems`·`sellItems`·`linkedItems`)를 함께 낸다 — `item_partner` 가 없는 DB 에서는 이 필드가 아예 없다(화면은 빈 칸) |
| `GET /api/admin/partners/:code` | `{ partner }` |
| `POST /api/admin/partners` | 코드 기준 upsert. **코드를 비우면 `P0001` 부터 비어 있는 번호를 찾아 채운다**(지워진 자리 재사용). 본문: `code?, name*, kind, bizNo, ceo, bizType, bizItem, tel, fax, email, zipcode, addr, mgrName, mgrTel, mgrEmail, payTerms, currency, status, note` |
| `PUT /api/admin/partners/:code` | 코드를 바꿀 때 |
| `DELETE` | **405** — 상태를 `CLOSED` 로 |

검증: **사업자등록번호는 형식(숫자 10자리)과 국세청 검증식**을 둘 다 본다(가중치 1,3,7,1,3,7,1,3,5 + 9번째 자리 ×5 의 십의 자리). 통과하면 `000-00-00000` 으로 정규화해 저장하고, 같은 번호가 이미 있으면 부분 UNIQUE 인덱스가 막는다(빈 값은 여러 건 허용). 이메일 형식, 거래구분·상태 열거도 400 으로 거른다.

### 12.3 화면

`public/js/partners.js`(`window.FWPartners = { mount(container, api) }`), 스타일은 **`css/items.css` 공용**(`.fwi-*`) — 품목 등록과 같은 구조라 새 CSS 를 만들지 않았다. 탭 `data-tab="partners"`(라벨 "🤝 거래처")·`#tab-partners`, `admin.js` 의 `mountPartners()`.
시트 13열(거래처 코드 · 거래처명 · 거래구분 · 사업자등록번호 · 대표자 · 업태 · 종목 · 전화 · 담당자 · **연결 품목** · 결제조건 · 통화 · 상태)에 품목 시트와 같은 규칙(고정 머리글·코드 열 고정·정렬·CSV·`pri` 폭 반응형)을 그대로 쓴다.

행을 누르면 폼 아래에 **역조회**가 붙는다 — `GET /api/admin/partners/:code/items` 로 그 거래처가 **대는 품목(매입)** 과 **사 가는 품목(매출)** 을 나눠 보여 주고, 각 행의 `품목 세부 →` 가 품목 세부 탭으로 넘긴다. 넘기는 방법은 탭 버튼을 눌러 모듈을 띄우고 `window.FWItemDetail.open(pn)` 을 부르는 것이다 — 그 시점에 mount 가 끝나지 않았으면 모듈이 품번을 예약해 두고 `reload()` 뒤에 연다. 연결을 **고치는** 곳은 품목 세부 한 곳뿐이다(양쪽에서 고칠 수 있게 하면 어느 쪽이 맞는지 헷갈린다).

### 12.4 품목 연동 (다음 단계)

품목 세부 등록 화면(하위 메뉴)에서 `item_partner` 로 붙인다 — 품목 × 거래처 × 역할(매입/매출) 에 공급사 품번·단가·리드타임·최소발주량. 그때 §11 에 절을 추가한다. 지금은 거래처 마스터만 있고 품목과의 연결은 없다.

## 11.5 품목 세부 · 거래처 연결 (스프린트 4 — owner: 최민준)

📦 품목 등록이 "품번을 만드는" 화면이라면, 품목 세부는 만들어 둔 품번 하나를 골라 **살을 붙이는** 화면이다. 좌측 메뉴에서 품목 등록의 **하위 항목**으로 들어간다.

### 11.5.1 `item_partner` — 품목 × 거래처

한 품목에 공급사가 여럿인 것이 정상이고 공급사마다 품번·단가·리드타임이 다르다. 그래서 품목에 `주거래처` 컬럼을 박지 않고 표로 둔다. `item`(ddl-v1.sql)과 `partners`(db.js)를 둘 다 참조하므로 **ddl 실행 뒤** `server/db.js` 가 만든다.

| 컬럼 | 뜻 |
|---|---|
| `item_id` · `partner_id` · `role` | 역할은 `BUY`(이 거래처에서 사 온다) · `SELL`(이 거래처에 판다). 셋이 UNIQUE — 같은 역할로는 한 번만 |
| `partner_pn` | 거래처 쪽 품번 (공급사 품번·고객 품번) |
| `price` · `currency` · `price_uom` | 단가. **원가 전개에는 쓰지 않는다**(참조값). `price_uom` 이 비면 품목 기준단위 |
| `lead_days` | 리드타임(일) |
| `order_uom` · `order_qty` | 이 거래처에 주문하는 단위와 환산(1 `order_uom` = `order_qty` × `base_uom`). 비우면 품목의 기본 입고단위를 따른다 |
| `moq` | 최소 발주량 — **발주단위 기준**이다(현장은 "최소 1박스"라고 말한다). 기준단위 환산값은 API 가 `moqBase` 로 함께 낸다 |
| `is_primary` | 주거래처. **품목·역할당 한 곳** — 부분 UNIQUE 인덱스(`WHERE is_primary = 1`)로 강제하고, 새로 켜면 API 가 기존 주거래처를 먼저 내린다 |
| `valid_from` · `valid_to` | 유효기간(`CHECK valid_to >= valid_from`) |

**거래구분과 역할이 어긋나면 400.** 매출 전용 거래처를 매입처로 붙이려 하면 막는다(`BOTH` 는 양쪽 다 된다) — 거래처 마스터를 잘못 고른 실수를 여기서 잡는다.

### 11.5.2 API

| 엔드포인트 | 계약 |
|---|---|
| `GET /api/admin/item-partners?pn=&partner=&role=` | `[{ id, pn, itemName, baseUom, partnerCode, partnerName, partnerKind, partnerStatus, role, roleName, partnerPn, price, currency, priceUom, leadDays, orderUom, orderQty, effOrderUom, effOrderQty, orderSource, itemInUom, itemInQty, moq, moqBase, isPrimary, validFrom, validTo, note }]` — 역할 → 주거래처 → 코드 순. `eff*` 는 아래 규칙을 적용한 **실제 쓰이는 값**이고 `orderSource` 가 그 출처(`partner`/`item`/`base`) |
| `POST /api/admin/item-partners` | `{ pn, partnerCode, role, partnerPn?, price?, currency?, priceUom?, leadDays?, moq?, orderUom?, isPrimary?, validFrom?, validTo?, note? }` |
| `PUT /api/admin/item-partners/:id` · `DELETE .../:id` | 수정 · 해제(연결은 전표가 아니라 기준이라 지운다 — 거래처 자체는 남는다) |
| `GET /api/admin/partners/:code/items` | 그 거래처가 대는(사 가는) 품목 |

자재 스키마가 안 올라온 DB 에서는 목록이 `[]`, 쓰기는 503 — 서버는 뜬다.

### 11.5.4 입고단위와 발주단위 — 어느 것이 이기는가

두 값이 같은 것을 가리키는 것처럼 보여서 한 번 못 박는다.

| | 어디에 | 뜻 |
|---|---|---|
| **기본 입고단위** | `item.in_uom` · `in_qty` | 이 품목을 보통 어떤 포장으로 받는가 (사내 표준) |
| **발주단위** | `item_partner.order_uom` · `order_qty` | **이 거래처에** 주문할 때 쓰는 단위 |

**적용 순서는 거래처별 발주단위 > 품목 기본 입고단위 > 기준단위(낱개)** 다. 공급사마다 포장이 다른 것이 보통이라 거래처 쪽이 이긴다. 서버가 이 규칙을 `orderUnit()` **한 곳에서만** 계산해 `effOrderUom`·`effOrderQty`·`orderSource` 로 내려 주고, 화면은 계산하지 않는다. 물려받은 값은 화면에 `*` 로 표시한다.

따라오는 성질 두 가지:
- **품목의 기본 입고단위를 바꾸면 따로 정하지 않은 거래처들이 같이 움직인다.** 의도한 동작이다 — 표준 포장이 바뀌면 예외를 두지 않은 곳은 따라가야 한다.
- **`moq` 는 발주단위 기준이므로 발주단위를 바꾸면 최소발주의 실수량도 바뀐다.** (2 CASE = 1,000 EA 였다가 단위를 BOX 로 바꾸면 2 BOX = 200 EA). 화면이 괄호로 기준단위 환산을 항상 같이 보여 주는 이유다.

재고·BOM·로트는 어느 경우에도 **기준단위**로만 돈다. 발주·입고 단위는 표기와 환산일 뿐이다.

### 11.5.3 화면 · 메뉴

`public/js/itemdetail.js`(`window.FWItemDetail = { mount(container, api) }`), 스타일은 `css/items.css` 공용(`.fwd-*` 몇 개만 추가). 구성: 품번 고르기(datalist) → ① 품목 요약(읽기) ② 식별정보(도면번호·GTIN·참조단가·이미지, `PUT items/:pn`) ③ **매입처·매출처 표**(연결·주거래 지정·해제) ④ BOM 요약(읽기 — 구조 편집은 📦 품목 등록과 🧩 자재 탭).

좌측 메뉴는 평면 탭에서 **3묶음**(운영 · 기준정보 · 설정)으로 바뀌었다. 묶음 제목을 누르면 접히고 상태는 `localStorage['fw.nav.<group>']` 에 남는다. `품목 세부` 는 `품목 등록` 아래 들여쓴 하위 항목(`button.sub`)이다.
시트가 있는 탭(`items` · `itemdetail` · `partners` · `materials`)은 `.content.wide` 로 **본문 폭 제한을 1100px → 1700px** 로 푼다 — 1100px 에서는 시트 열이 접힌 채로만 보였다.

## 13. 화면 공통 — 상세 위치 토글 (스프린트 4 — owner: 최민준)

목록 + 상세로 된 화면이 셋이 되면서(📦 품목 등록 · 🤝 거래처 · 🧩 자재) 같은 토글을 세 번 만들 이유가 없어 `public/js/fwlayout.js` 하나로 뺐다.

```js
FWLayout.mount(slotEl, { key: 'items', target: splitEl, def: 'right', onChange })
FWLayout.get(key, def)  ·  FWLayout.set(key, pos)  ·  FWLayout.apply(target, pos)
```

- `target` 에 **`pos-below` / `pos-right`** 클래스만 붙인다. 실제 배치는 각 화면 CSS 가 그 클래스로 정한다 — **JS 는 폭을 재지 않는다.**
- 고른 값은 `localStorage['fw.layout.<key>']` 에 화면별로 따로 남는다(`items` · `partners` · `materials`).
- **폭이 모자라면 CSS 가 지정을 무시하고 아래로 내린다**(`@container`: 품목·거래처 1200px, 자재 1300px). 사용자가 오른쪽을 골라 둔 채 창을 줄여도 깨지지 않는다.
- 기본값은 셋 다 `right`.

### 13.1 시트 열 숨김의 기준 (`fwisheet`)

품목·거래처 시트의 `pri` 열 숨김은 **시트가 실제로 놓인 칸**(`.fwi-sheetcol`, `container-name: fwisheet`)을 본다. 탭 전체 폭(`fwi`)을 기준으로 두면 상세를 오른쪽에 뒀을 때 시트 칸이 좁아진 것을 모르고 열을 다 그려 가로 스크롤이 생긴다 — 실제로 그렇게 만들었다가 고쳤다. 실측(탭 폭 1629px): 상세를 아래에 두면 시트 1629px·**15열**, 오른쪽에 두면 시트 1147px·**11열**, 둘 다 가로 넘침 0.

`.fwi-layout`(토글 버튼 모양)은 `css/items.css` 한 곳에 있고 자재 탭도 그대로 쓴다 — 콘솔이 두 CSS 를 다 읽는다.
