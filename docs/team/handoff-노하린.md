## 한 줄 결론

> **구조는 맞다. 제약이 비어 있다.**
> 실데이터 60품목이 막힌 행 0건으로 들어가고 노드 60 − 간선 59 = 1 로 정확히 트리다.
> 그런데 **반례 31건 중 16건이 그대로 들어간다.** 그리고 **DDL 이 원문 그대로는 실행되지 않는다.**

| | 확인 | 결함 | 의견 | 미실시 |
|---|---:|---:|---:|---:|
| 합계 | **99** | **35** (→ 정리하면 **D-1~D-21**) | 1 | 2 |

> 막히는 15건은 **전부 DDL 의 `CHECK`·`FK`·`UNIQUE` 가 잡은 것**이다 — 제약을 건 자리는 정확히 동작한다.
> 뚫리는 16건은 **전부 "트리거로 하겠다"·"적재 계층에서 하겠다"고 적고 코드가 없는 자리**다.
> **문제는 설계 사상이 아니라 미완성이다.**

## 윤태경에게 — 다음 라운드에 **반드시** 고쳐야 할 5건

나머지는 v1.1 로 미뤄도 된다. 이 다섯이 고쳐지면 **서명한다.**

### 1. D-19 — §5.1 `uom_conv` DDL 이 실행되지 않는다 (치명)

```
OperationalError: expressions prohibited in PRIMARY KEY and UNIQUE constraints
  → PRIMARY KEY (from_uom, to_uom, COALESCE(item_id, 0))
```

SQLite 는 **테이블 제약에 식을 못 쓴다. 인덱스에는 쓸 수 있다.** python 3.50.4 · node:sqlite 3.53.0 **둘 다** 같은 이유로 거부한다.
네가 `ux_bom_line_dup` 에서 이미 쓴 그 방법으로 옮기면 된다:

```sql
CREATE TABLE uom_conv ( from_uom TEXT NOT NULL REFERENCES uom(uom_code), ... item_id INTEGER REFERENCES item(item_id) );
CREATE UNIQUE INDEX ux_uom_conv ON uom_conv(from_uom, to_uom, COALESCE(item_id, 0));
```

> `PRIMARY KEY (from_uom,to_uom,item_id)` 로 바꾸는 건 **안 된다.** SQLite 는 rowid 테이블 PK 열에 NULL 을 허용해
> 전역 환산이 무제한 중복된다. 식 인덱스여야 한다. (TC-56d 로 확인했다)

### 2. D-3 — 순환 차단이 **이행 적재 구간 내내 꺼져 있다** (치명)

이게 이번 라운드에서 제일 큰 발견이다.

- `bom_header.status` 기본값 = `'DRAFT'`
- R-1 트리거 CTE = `h.status IN ('APPROVED','ACTIVE')`
- → **DRAFT 사이의 순환은 하나도 안 잡힌다.** `A→B→A` 가 그냥 들어간다. 양 런타임 동일.
- 이행 [1] 병행 적재가 **바로 그 상태**다. 현행 데이터에 자기참조 2건이 실제로 들어 있는 시스템에서, 옮기는 순간에 방어가 없다.

자기참조(`A→A`)만 잡히는 건 `depth=0` 시드가 `bom_header` 를 안 거치기 때문이다.
**즉 네가 기대값으로 적은 `FS-7010 → FS-7010` ABORT 는 맞지만, 그 성공이 나머지를 가린다.**

고칠 곳은 한 줄이다: `AND h.status <> 'OBSOLETE'`.
구조 무결성은 승인 상태와 무관하다 — "DRAFT 니까 순환이어도 된다"는 성립하지 않는다.

### 3. D-5 — `bom_line` **UPDATE 트리거가 없다** (치명)

초안 §6 에 "UPDATE용 동일 트리거 1개를 추가한다"고만 적혀 있고 코드가 없다.
실제로 `UPDATE bom_line SET child_item_id=?` 한 번으로 `A→B→A` 를 만들었다. R-9(유효일자)도 같은 문제다(D-7).
**INSERT 만 막는 규칙은 규칙이 아니다.**

같은 김에 D-1 도 함께: 가드를 `d.depth < 64` 로 올리고 **한계 도달 시 별도 RAISE**.
지금은 길이 12 이상 순환이 통과하고, 메시지는 "레벨 초과"라면서 **레벨 초과로는 한 번도 raise 되지 않는다.**
비용 걱정 없다 — 10단 전개 INSERT 가 행당 **0.019 ms(py) / 0.043 ms(node)**, 1만 라인 일괄 적재가 **57 ms** 다.
**"최대 레벨 10"(R-2)은 순환 트리거에서 떼어내 별도 점검 쿼리로 분리해라.** 한 문장이 두 일을 하려다 둘 다 놓치고 있다.

### 4. D-10 — 이행 [3] 호환 뷰가 §10.3 계약을 **스스로 깬다** (치명)

네가 직접 못 박은 계약이다 — "`inputs[]` 의 키와 **의미**를 바꾸지 않는다".

```
process_inputs 뷰 교체:  36행 → 48행
전에만 1건 : OP-B90 → PE-6000 (팬텀이라 IN 행이 사라진다)
후에만 13건: SC-1010P, IP-1040, LC-1080, PK-0010, OP-B90 의 PE 부품 9종
```

행 집합이 달라지는 건 정제의 의도된 결과다. 문제는 **`qty` 의 의미**다.
뷰의 `qty` 는 `bom_line.qty_per` = **부모 `base_qty` 당**, 기존 컬럼은 **완성품 1대당**이다.
지금 값이 같아 보이는 건 **`parentPerProduct` 가 전부 1.0** 이기 때문이다 — **네가 P-7 에서 "위험 신호"라고 쓴 그 조건.**

수치로 고정해 뒀다(TC-57b): `GB-8000` 을 완성품당 2개로 바꿔도 뷰의 `GB-8010` 은 **1.0 그대로**다. 2 가 되어야 한다.
→ 뷰는 `qty_per` 가 아니라 **전개로 계산한 완성품당 소요량**을 내보내야 한다. 최민준과 재협의 필요.

### 5. D-15 — 로트 계보에 **무결성 장치가 하나도 없다** (치명)

V-9 는 성공했다. 코일 밀시트 `MS-8842` → 완성품 시리얼 `SN-BLDC-2026-000481` 까지 **정·역 양방향 완주**했다.
`lot_genealogy` 한 행에 자재·공정·설비·작업자·실적이 같이 들어간다 — "4M 이 여기서 만난다"는 말은 **사실이었다.**

그런데 그 축에 방어가 전혀 없다:

| 넣어 본 것 | 결과 |
|---|---|
| `lot_genealogy.in_lot_id = out_lot_id` (자기참조) | **들어간다.** R-13 이 규칙표엔 "CHECK"라 적혀 있는데 §5.6 DDL 에 그 CHECK 가 없다 (D-14) |
| 계보 순환 (`A→B` 있는데 `B→A` 추가) | **들어간다.** 추적 쿼리가 무한 루프한다 |
| `mat_lot.parent_lot_id` 로 부모↔자식 맞물림 | **들어간다** |
| 같은 계보 행 2번 (`process_id` 가 NULL) | **둘 다 들어간다.** SQLite 는 NULL 을 서로 다르게 본다 (D-16) |

**감사에서 답을 내는 것과, 그 답이 맞다고 보증하는 것은 다른 일이다.**

## 최민준에게 — 요청 1건 (2단계 전에)

**`process_inputs` 호환 뷰 방식은 지금 형태로는 성립하지 않는다** (계획서 이행 [3], V-10).
`server/index.js` 를 무수정으로 두겠다는 전제가 깨진다:

- 행 수 36 → 48 (정제의 의도된 결과)
- **`qty` 의 의미가 바뀐다** — 뷰는 "부모 base_qty 당", 기존 컬럼은 "완성품 1대당"
- 지금은 `parentPerProduct` 가 전부 1.0 이라 **값이 우연히 같다.** 서브어셈블리가 2개 되는 순간 화면 숫자가 틀린다

재현: `docs/4m/prototype/v09` → `python r2_load.py && python r2_tests.py` → `out/05_tests.log` 의 TC-57 · TC-57b.

**부탁 2가지**
1. 뷰가 `qty_per` 대신 **전개 계산값**을 내보내는 형태로 가도 되는지 의견. (성능은 문제없다 — 전개 23 ms/1만행)
2. 확정되면 **운영 DB 의 실제 24공정 투입 단품 표**로 전후 비교를 해야 한다. 나는 이번에도 운영 DB 를 열지 않았고,
   `prereq_existing.sql` 은 `server/db.js` 에서 옮긴 **스키마 사본**이라 실 데이터 대조는 미실시로 남겼다.

참고로 인터페이스 §7/§8 문서는 네 소유다. `parts` 스키마 변경안이 확정되면 그때 알리겠다.

**스키마가 v1.0 으로 바뀌면** `ddl_v09_raw.sql` 을 새 원문으로 갈아 끼우고 위 순서대로 다시 돌린다.

> `bomsql.py` 머리말을 꼭 읽어라. **계획서에 전개 SQL 이 한 줄도 없어서** 내가 4가지 규칙을 직접 정했다

> 지금은 구현자마다 다른 답이 나올 수 있다.

### 운영 DB 를 복사해서 볼 일이 있으면

`factory.db` 와 `factory.db-wal` 을 **같이** 복사하고 `factory.db-shm` 은 **복사하지 마라.**
남의 shm 을 들고 가면 SQLite 가 WAL 색인을 잘못 읽어 **테이블이 1개만 보인다** (라운드 1 에 실제로 겪었다).
